# 排查结论输出

按问题复杂度组织结论，先给出已确认的直接原因，再给支撑证据与影响。没有足够证据时明确区分假设和待确认项。

## 必要内容

```text
【根因】
[已确认原因；如果未确认，说明当前能证明什么]

【关键证据】
- 环境、服务和实际部署版本：
- 脱敏关联标识与精确时间窗口：
- 日志、数据或代码位置：

【业务影响】
[影响范围、状态、重试或后续流程；未知项明确标注]

【处理建议】
[需要执行的动作、对应授权、验证方法与剩余事项]
```

能定位代码时给出实际项目和行号；只取得日志或数据时，直接说明代码链路尚待核实。

## 时间线

单点异常可以省略时间线。跨服务、MQ、回调、重试或状态迁移影响判断时，补充二到六个关键事件，写明时区与先后关系。不要搬运完整日志或为了填模板堆流水账。

## 虚构示例

以下只演示证据表达，不代表已验证的环境事件：

```text
【根因】
example-worker 处理测试消息时，依赖记录缺失；当前分支访问空对象，导致该次消费失败。

【关键证据】
- 测试环境；服务 example-worker；版本 <实际 SHA>
- trace <脱敏标识>；时间 <开始时间> 至 <结束时间>
- <实际仓库/路径:行号> 的缺失记录分支与异常栈一致

【业务影响】
该次消费失败已确认。是否重试、进入死信或影响其他消息，需要继续核对消费配置和运行日志。

【处理建议】
确认缺失数据的来源及业务约定，再选择修复；重试或补偿须有对应授权，并验证相同关联范围。
```

公共模板不保存真实手机号、人员、客户、业务主键、内部服务路径或具体事故快照。
