# 标准结论输出模板

## 统一骨架

线上排查结论默认按下面 6 块输出：

```text
【根因】
[一句话讲清楚本次失败或异常的直接原因]

【链路时间线】
1. [时间点] [发生的事件]
2. [时间点] [发生的事件]
3. [时间点] [发生的事件]

【关键信息】
- 服务 / 应用:
- 部署区:
- 关键 ID:
- 异常类型 / 当前状态:

【代码位置】
- [项目路径:行号]
- [项目路径:行号]

【业务影响】
- [这条失败影响什么]
- [是否会重试 / 是否会进入死信 / 是否影响其他数据]

【处理建议】
1. [立即处理动作]
2. [验证动作]
3. [后续修复动作]
```

## 使用原则

- 必须有 `【根因】`
- `【链路时间线】` 按需展开，不是每次都必须写满
- 必须说明 `【业务影响】`
- 必须给出 `【处理建议】`
- `【代码位置】` 能定位到项目和行号时就写；如果当前只查到日志和数据，也要明确说“代码位置待继续定位”

## 时间线规则

`【链路时间线】` 不是流水账，只在它影响判断时展开。

### 可以省略时间线的情况

- 单点异常已经能直接定性
- 一条日志或一次查询就能给出根因
- 用户只要一句结论或快速判断
- 问题没有跨服务、重试、异步链路

这类情况可以：

- 不写 `【链路时间线】`
- 或只写 1 到 2 行关键时间点

### 应该补时间线的情况

- 涉及跨服务调用
- 涉及 MQ 消费、重试、死信
- 涉及回调、补偿、异步任务
- 涉及状态从 A 变到 B 再变到 C
- 涉及智能任务 / 流程节点流转
- 需要证明“问题不是单点报错，而是一段链路问题”
- 后续要复盘或转交他人继续处理

### 时间线写法

- 只写关键节点，不抄整段日志
- 重点写“先发生什么，后发生什么，最终停在哪”
- 时间点优先写：
  - 关键异常时间
  - 状态变化时间
  - MQ / 回调 / 节点执行时间
- 如果数据库 `alter_time`、日志时间、MQ 时间不完全一致，优先选最能解释链路的那个时间

### 推荐长度

- 简单问题：0 到 2 行
- 中等复杂问题：2 到 4 行
- 复杂异步链路：4 到 6 行

超过这个长度，优先压缩成“关键节点”，不要写成流水账。

## 示例 1：技术 Trace 排查

```text
【根因】
sms-consumer 在处理挂断短信状态回调时，`smsExtend` 为空，代码直接调用 `getSendPlanGroupId()`，触发 NPE。

【链路时间线】
1. 2026-07-08 10:12:14
   海外 sms-consumer 收到挂断状态消息
2. 2026-07-08 10:12:14
   `SmsReportService.handleHangupStatusReport` 进入处理
3. 2026-07-08 10:12:14
   `SmsReportService.buildSmsStatusEvent` 访问 `smsExtend.getSendPlanGroupId()` 抛 NPE
4. 2026-07-08 10:12:14
   消息消费失败，进入重试链路

【关键信息】
- 服务 / 应用: `sms-consumer`
- 部署区: 海外
- 关键 ID: `traceId=fe650d50a6be0dae`, `smsId=374318962`
- 异常类型 / 当前状态: `NullPointerException`

【代码位置】
- `message/sms/consumer/.../SmsReportService.java:3000`
- `message/sms/consumer/.../SmsReportService.java:3003`

【业务影响】
- 当前这条短信状态回调处理失败
- 如果消息重试后仍失败，会进入死信
- 下游客户可能收不到对应状态更新

【处理建议】
1. 给 `smsExtend` 增加判空和降级处理
2. 用 Archery 查 `ai_sms` / `ai_sms_extend`，确认这类空数据是否为单条脏数据还是批量问题
3. 修复后补消费死信或手动补偿这批失败记录
```

## 示例 2：号码为什么没导入任务

```text
【根因】
号码没有进入 `ai_task_detail`，不是“导入后没流转”，而是导入阶段就被重复去重拦截了。

【链路时间线】
1. 2026-07-08 08:31:02
   任务 `taskId=354186` 开始导入
2. 2026-07-08 08:31:05
   导入服务处理号码 `138****8000`
3. 2026-07-08 08:31:05
   命中重复校验逻辑，未写入 `ai_task_detail`
4. 2026-07-08 08:31:06
   导入批次继续处理其他号码，任务整体未中断

【关键信息】
- 服务 / 应用: `call-task`
- 部署区: 国内
- 关键 ID: `taskId=354186`, `号码=138****8000`
- 异常类型 / 当前状态: 未导入成功，命中去重

【代码位置】
- `call/call-task/server/.../ImportTaskService.java`
- `call/call-task/server/.../TaskDetailDeduplicateService.java`

【业务影响】
- 这个号码不会进入后续外呼和流程链路
- 任务整体仍可继续执行，不影响其他号码

【处理建议】
1. 先确认这个号码是否符合业务预期地应该去重
2. 如果不应该去重，检查任务维度去重条件和历史数据
3. 如果运营需要补数据，补导入该号码后再观察是否进入 `flow_data`
```

## 示例 3：智能任务没流转

```text
【根因】
流程实例已生成，但在前置一致性检查时发现存在等待执行的节点，当前 requestId 被卡住，未继续流转。

【链路时间线】
1. 2026-07-08 14:03:11
   号码进入任务并生成 `flow_data`
2. 2026-07-08 14:03:12
   `ai-flow-server` 进入节点执行前校验
3. 2026-07-08 14:03:12
   `DbConsistencyChecker.checkAndGetExecutingData` 抛 `DataInconsistencyException`
4. 2026-07-08 14:03:12
   当前节点未继续执行，流程停在等待状态

【关键信息】
- 服务 / 应用: `ai-flow-server`
- 部署区: 国内
- 关键 ID: `taskId=...`, `flowDataId=...`, `requestId=2459204585722880`
- 异常类型 / 当前状态: `DataInconsistencyException` / 存在等待执行节点

【代码位置】
- `call/ai-flow/ai-flow-server/.../DbConsistencyChecker.java:37`
- `call/ai-flow/ai-flow-server/.../BaseFlowListener.java:115`

【业务影响】
- 当前号码不会继续流转到下一节点
- 如果没有人工干预或补偿，这条流程会一直卡住

【处理建议】
1. 先用 Archery 查 `flow_task_node_data`，确认对应 `requestId` 当前状态
2. 判断是上游节点未完成、锁未释放，还是异常状态未清理
3. 处理卡住节点后，再决定是否重试流转或做数据补偿
```
