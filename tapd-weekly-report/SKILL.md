# TAPD 周报生成

## 概述

根据给定版本号（按周四日期命名）从 TAPD 拉取需求，生成一份周报草稿，并写入仓库内的 `reports` 目录。

## 工作流

1. 先确认版本号。
   - 把用户提供的版本视为本周版本（周四日期）。
   - 如果用户没有提供下一个版本，默认按 `+7 天` 推导。
2. 确认环境变量。
   - `TAPD_TOKEN` 必填
   - `TAPD_WORKSPACE_ID` 可选，默认 `10000000`
3. 运行脚本拉取需求并生成周报：

```bash
python3 scripts/tapd_weekly_report.py --version 2026-0115 --next-version 2026-0122
```

4. 把生成结果当作草稿，再与上一周同目录下的周报进行对比。
   - 重点对比上一周的 `下周计划`
   - 对照本周的 `本周完成`
   - 对照本周的 `下周计划`
5. 在定稿前先审查计划执行情况：
   - 已完成项：上周 `下周计划` 中，本周出现在 `本周完成` 的事项
   - 顺延项：上周 `下周计划` 中，本周仍出现在 `下周计划` 的事项
   - 去向不明项：上周 `下周计划` 中，本周既不在 `本周完成`，也不在 `下周计划` 的事项
   - 插单项：本周 `本周完成` 中，上周 `下周计划` 里没有出现的事项
6. 如果存在去向不明项、没有原因的顺延项，或疑似改名但无法确认的事项，先向用户确认状态和原因，再写最终版周报。
   - 不要静默丢掉原计划事项
   - 不要编造延期原因
7. 标准输出保持 4 个板块：
   - `本周概览`
   - `下周重点与风险`
   - `本周完成`
   - `下周计划`
8. 在概览区明确写出计划执行情况：
   - 上周计划总数
   - 本周完成数
   - 顺延到下周的数量
   - 去向不明数量（仅在确认后仍存在时写）
   - 插单数量
9. 如果顺延项或去向不明项已经从用户或上下文中确认原因，把原因写入 `下周重点与风险`。
   - 如果原因仍未知，要明确写“原因未确认”，不要编造。
10. 最后做一轮文案清理：
   - 客户名保留在括号中
   - 修正常见空格问题
   - 明显重复的父子任务合并为一项
   - 先压缩概览摘要
   - 详细到人的任务区仍然作为事实台账保留

## 归类规则

- 团队成员：成员甲、成员乙、成员丙
- `owner` 里没有这些成员的需求忽略
- 只有成员丙 -> 归到成员丙
- 成员丙 + 成员甲 -> 归到成员甲
- 成员丙 + 成员乙 -> 归到成员乙
- 成员丙 + 成员甲 + 成员乙 -> 归到成员甲
- 只有成员甲 -> 归到成员甲
- 只有成员乙 -> 归到成员乙
- 成员甲 + 成员乙（没有成员丙）-> 默认归到成员甲，除非用户另行说明

## 输出规则

- 去掉需求标题中的 `【】` 标签前缀
- 周报中不要写需求 ID
- 优先使用规范化表达，例如 `OpenAPI 接口`、`（客户名）`
- 先生成简明摘要，再保留按人的详细任务区；除非标题本身需要规范化，否则不要改详细区原意
- 在摘要里抽取客户或项目时，优先使用标题中明确的客户/项目标签
  - 过滤通用能力词、流程状态词、截断动作词，例如 `进行中`、`外呼回调`
- `本周概览` 应覆盖：
  - 人员工作量分布
  - 本周主要交付主题
  - 计划执行摘要：计划 / 完成 / 顺延 / 去向不明 / 插单
- `下周重点与风险` 应覆盖：
  - 下个版本的人数分布
  - 标题里能可靠识别的重点客户 / 项目
  - 继续顺延到下周的事项
  - 已确认的延期原因
- 如果父任务和子任务明显描述的是同一条交付线，只保留一项
  - 优先保留范围更清晰、交付内容更具体的标题
  - 合并后要重新计算数量
- 如果两周之间只是标题改名，但语义明显是同一项，要手工修正周报对比结果，不要机械误判
- 在保存周报前，如果计划执行情况无法从现有数据解释清楚，要先追问用户
  - 优先用一条简洁的汇总问题，把待确认事项列出来
- 保存路径固定为：
  - `reports/YYYY/MM/weekly-report-YYYY-MM-DD.md`
  - 其中日期取版本所在周的周一
