# 文章形态选择

先识别当前对话形成了哪一种可复用知识，再选择结构。标题不手工编号，章节可以按内容删减或合并。

## 概念学习

适用于理解了一个新名词、抽象概念或认知模型。

```text
写在前面
核心概念
它解决了什么问题
如何理解或运作
实际示例
常见误区
适用场景与边界
总结
```

重点记录“原来怎么理解、现在为什么理解得更准确”，避免只抄定义。

## 技术机制

适用于学习调用链、发现机制、协议行为、生命周期或系统内部关系。

```text
背景
整体模型
关键组件
状态、数据或调用流程
关键边界条件
实际案例
总结
```

优先解释组件关系和因果链；只有在能显著降低理解难度时才加入图示。

## 故障排查

适用于有明确异常、证据链和已验证处理结果的内容。

```text
问题现象
环境与前提
排查过程
根本原因
解决方案
验证方法
适用范围与注意事项
总结
```

保留决定性的错误信息和检查命令，删除没有信息价值的重复尝试。

## 操作教程

适用于一套可以复现的安装、配置、迁移或使用流程。

```text
目标
前置条件
操作步骤
关键配置说明
验证方法
常见问题
回滚或影响范围
总结
```

每个关键步骤说明执行位置、预期结果和失败表现。

## 工具对比

适用于比较多个工具、方案或工作模式。

```text
对比背景
候选对象
对比维度
核心差异
实际场景
选择建议
限制与例外
总结
```

选择建议必须绑定场景和条件，不给脱离前提的绝对排名。

## 技术决策

适用于沟通中形成了架构、命名、作用域或流程选择。

```text
决策背景
目标与约束
候选方案
权衡过程
最终选择
后续影响
何时需要重新评估
总结
```

把事实、假设和偏好分开，说明没有选择其他方案的具体原因。

## 经验总结

适用于实践中形成了可迁移的方法、判断标准或工作习惯。

```text
场景
原有做法或认识
新发现
实践证据
可复用原则
不适用的情况
总结
```

不要把个人偶然经验扩大成普遍规律；明确样本和适用范围。

## 灵感提纲

适用于信息还不够写成完整文章，但值得先保存。

```text
核心想法
为什么值得写
读者可能关心的问题
暂定文章结构
已有材料
待验证问题
```

使用 Markdown 注释保存内部待办，保持 `draft: true`，不要为了完整度补写未经证实的内容。

## 组合原则

- 先确定一个主形态，再按需要吸收另一个形态的一到两个章节。
- 概念学习可以加入技术机制，但不要演变成源码堆砌。
- 故障排查可以加入操作教程，但必须区分诊断命令和最终配置。
- 工具对比可以解释技术决策，但结论必须与对比证据一致。
- 快速捕获优先保留知识和证据；完整初稿再优化叙事和过渡。
