# 从纠正中建立约束

同一机制的错误在多次反馈、审查或任务中反复出现时，检查现有防线为何失效，再选择能减少复发的改进。一次新需求、偏好变化或孤立失误不自动升级成通用规则；没有可靠重复证据时，先处理当前问题并保留判断边界。

## 先确认错误类别与范围

- 用当前任务及已掌握的记录找出具体错误、共同原因和已尝试的防线，区分需求改变、规则冲突、信息缺失和执行错误。不要为复盘全量扫描历史或无关仓库。
- 已授权的当前修复先完成；不能用整理规则拖延交付，也不能因发现重复问题就扩大架构改造、全局配置或跨仓修改。只能建议的改进留作建议，实际修改继续按已有授权判断。

## 选择能生效的约束

优先考虑下列层级，选择符合实际缺口、兼容要求和授权范围的最小改进。优先级不是强制重构顺序；更高层改造成本过大或超出范围时，说明原因并采用可行的约束。

1. **结构与数据模型。** 调整所有权、状态表达或接口边界，让错误状态或错误路径难以出现。
2. **类型与自动检查。** 用类型、边界校验、权限、lint 或 CI 阻止错误；错误信息应能指出修正方向。
3. **行为测试。** 对实际失效的可观察行为补最少必要的检查，不靠匹配提示词或标题证明约束有效。
4. **文档与 Agent 指令。** 处理无法可靠自动检查的判断，或给已生效机制提供入口。更新原有规则的唯一维护位置，避免每次失误都追加一条绝对要求。

例如，反复出现未分类条目时，可在配置读取边界拒绝缺失或未知分类，并保留合法分类的行为；只有提醒“记得分类”，不能证明错误已被阻止。反复漏审已提交代码时，应补范围交接及行为检查，而非仅要求“认真审查”。例子不自动授权修改无关安装器或项目。

## 证明约束针对了旧错误

在隔离样例或已有安全验证路径上重放代表性旧错误，证明新约束会拒绝或捕获它，同时确认合法输入与相关兼容行为仍成立。可比较修复前后，或在临时副本中构造明确的错误变体；不为证明防线而破坏共享环境、用户现场或生产数据。

无法运行检查时，说明已实现内容和待验证部分，不能声称已防止复发。涉及 Skill 的改进可用行为评估检查实际操作，静态格式或文本一致性检查不能替代它。

需要持久化时，在原有任务记录或规则旁简要关联“错误类别 → 生效约束及位置 → 检查入口与证据/限制”。不强制新建复盘文档、检查台账或总进度，也不把历史计划当作后续操作授权。结论只覆盖已检查的机制与场景，不从一次通过推断所有任务都不会再犯。
