# 按任务类型选择执行方法

本文件补充通用流程，不另建交付阶段。只读调查可以收集证据、提出假设和建议，不自动进入修复、实验写入或发布；实施和外部操作继续按已有授权及专项技能执行。只读取与当前任务有关的部分。

| 类型 | 本次要证明什么 |
|---|---|
| 缺陷修复 | 原触发条件下的错误得到解释，修复后预期成立，相关回归未被破坏 |
| 性能优化 | 指标和工作量相同，测量有效，改动改善了目标路径或明确说明没有可测收益 |
| 新功能 | 已确认的可观察结果在实际入口成立，已有相关行为保持兼容 |
| 行为保持的重构 | 明确列出的外部行为在相同输入和条件下保持一致，避免夹带行为修正 |

## 缺陷修复

1. **确定故障与触发条件。** 依据契约区分预期和实际，记录输入、状态、版本及观察入口。优先用已有测试或安全的本地路径复现；线上日志等历史证据用于定位，不等于当前已复现。不能直接复现时，缩小条件或增加必要观测，并说明未复现的边界。不得为复现擅自操作生产、共享数据或其他未授权资源。
2. **用证据筛选原因。** 沿真实链路形成少量候选解释，优先做能区分它们的检查。区分已观察现象、已确认机制和待验证假设。证据推翻假设时，撤回本任务中仅由该假设引出的试探性改动，不覆盖用户或其他人的改动；不要堆叠“可能有用”的防御分支。
3. **按确认的原因修复。** 修改应能解释原故障为何发生、为何不再发生。临时规避、风险缓解与根因修复分别说明，不把未证实的解释作为事实。已有便宜稳定的本地测试路径时，可先保留失败用例再修复；不强制 TDD，也不用更多 mock 代替所缺的运行证据。
4. **回到原条件验证。** 尽量在同一入口、同类输入和触发条件下取得修复前后结果，并补受影响的关键回归。环境或条件不一致时标明差别及其限制；未运行、未复现或结果不确定均不能算通过。报告故障、根因或剩余假设、改动和对应版本的验证证据，记录要求沿用原主记录。

## 性能优化

1. **先定义指标和基线。** 明确用户等待的路径、输入规模、单位及目标指标，例如端到端延迟、吞吐或峰值内存。确定比较版本与未提交范围，先确认瓶颈；不凭局部代码观感宣称性能问题或收益。
2. **让比较有效。** 对齐数据、并发、构建方式、依赖、资源限制和缓存冷热状态；有意改变的条件单独列出。计时区间必须包含要比较的工作。核对结果正确性、实际完成量、超时和错误率，少做工作、提前失败或降低输出质量带来的数字不能当作加速。
3. **按波动重复测量。** 在成本允许且已获授权的环境中交替运行前后版本，按稳定性选择次数，报告样本数、代表值及波动范围。调查异常值和明显不合理的收益，检查瓶颈是否转移、局部改善是否反映在端到端路径；不强制固定样本数或额外线上压测。
4. **按证据下结论。** 区分更快、更慢、无可测差异和证据不足，附版本、命令或可复查产物及关键条件。不能测量时只交付代码层分析、拟验证方案或限制，不报告未经测量的收益。复用仍有效的结果，后续改动按通用验证规则判断哪些证据需要补验。

## 新功能与行为保持的重构

- 新功能先把已确认目标对应到实际入口和可通过或失败的检查，再实现所需差异。不能从需求中的实现建议直接推导新增接口、字段或抽象，继续按影响分析核对已有能力。
- 重构先说明保持哪些用户可观察行为，包括空值、错误、配置默认值、顺序和副作用等本次相关契约。复用代表性输入做前后比较；发现原行为有问题时单独提出，不在重构中顺手改变。

所有类型的验证层级、证据对应版本和阻塞处理统一按 [验证与审查](verification.md) 执行，不在这里重复维护。
