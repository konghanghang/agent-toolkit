# 验证与审查

## 按风险选择验证

以下检查按改动适用性裁剪：代码检查行为和契约；脚本检查实际输入输出及适用平台；配置检查解析、消费方与生效方式；Skill 检查触发边界、引用和流程一致性；文档检查事实、链接和示例。无运行态的任务不强制环境验收，无 Git 的任务用实际文件范围标识版本。

- 优先从项目文档、CI 和已有脚本确定测试、编译、lint 命令，不猜命令。
- 业务行为变更和缺陷修复从已确认行为与相关数据分支选择测试，验证外部可观察结果和关键回归；不强制 TDD，也不逐个测试边界要求用户批准。拒绝或回退用例必须有业务契约或实际风险依据，不能仅因实现中新增了限制就把它当成正确预期。
- 接口契约变化时，验证已识别调用方的实际处理方式，尤其请求序列化、响应解析类型和结果使用。仅 Controller 或 Service 单测通过，不能证明跨服务兼容；未验证的调用方边界必须明确列出。
- 优先复用已有测试和编译验证；只有本次改变可观察业务行为、外部契约或关键回归边界，且现有测试无法覆盖时，才新增最少必要的单测。按会独立出错的行为选代表用例，不按修改方法、Controller、入口或参数组合逐一补齐；方案收敛或撤销后清理重复断言、只锁定实现细节或旧方案的用例。单测无法证明配置注入、跨服务等边界时，按风险使用相应层级的验证，不用更多 mock 用例代替。
- 文档、机械调整等低风险改动使用对应校验，不为形式新增测试。真实浏览器、服务或数据库验证仅在任务需要且具备条件时执行，遵守对应技能边界。
- 复用已通过且仍有效的结果；测试跳过、缺少环境、执行失败分别报告，不能算通过。

## 审查完整任务差异

开发结果交付前核对已确认范围和关键验收点，检查需求涉及的已有提交、暂存、未暂存及相关未跟踪文件。不能只审最后一次修改，也不能把其他人的无关改动当成本次成果。同时核对本轮新增或修改的单测是否必要、重复或只锁定实现细节，不另建测试台账，也不设固定用例数。

按实际基线、任务提交及工作区变化确认范围；基线或任务归属不明确时说明缺口，不能声称完整审查通过。对照影响分析中的实际入口与相关分支，检查实现和验证是否漏掉同步方向、另一数据源或调用方；不能只检查已经修改的文件。重点检查需求遗漏、外部契约和兼容性；涉及租户、SQL、配置或跨仓联动时核对相应边界是否齐全。

委派审查时，由主 Agent 明确交接任务目标与验收点、仓库及实际基线 ref/SHA、属于本任务的提交范围、相关暂存/未暂存/未跟踪文件，以及排除项。引用已有任务记录即可，不强制新建交接文件；不能只说“审一下”就把子 Agent 默认的工作区检查当作完整任务审查。任务提交与其他改动混在一起时，先划清归属，不默认把整个分支算成本任务。

主 Agent 核对子 Agent 返回的实际覆盖版本、范围和缺口，再综合结论。工作区干净不代表没有已提交的任务差异；空 diff 不代表整个任务无问题。仅完成部分审查时，明确已查范围与未覆盖项，不据此放行完整任务。未委派时由当前 Agent 按同一范围要求审查。

首次合入目标分支前，确认拟合入版本的任务差异已按上述范围审查；同版本结果直接复用，只补审新增或未覆盖部分，不因合入而重扫工作区或重跑无关测试。涉及业务配置时，追到实际读取、注入和刷新链路，核对未配置、空值及更新后的语义，不能只凭 setter 或 mock 测试认定配置生效。涉及前后端或多服务时，按同一操作场景核对各实际入口的结果，并标明尚未执行的环境验证。

审查或用户反馈指出一处可能重复的实现问题时，定向检查本任务差异中的同类改动，逐一修正或说明保留理由；不扩展为无关模块的全局搜索。

小改动直接报告结论；复杂任务在已有记录中留简短审查结论。满足 [Agent 分工](agent-orchestration.md) 的独立运行验证或复杂/高风险审查条件时，主动使用 `verifier` 或 `reviewer`；其余由当前 Agent 完成。不固定要求独立报告或机器门禁；用户明确要求正式报告时再按要求扩展。

## 核对需求记录

已建档的任务在开发交付和提测前，按项目记录规则核对处理方案正文、核心图（如有）、实际实现和测试预期是否一致。重点核对关键分支、优先级、兼容行为、配置生效和异常结果；方案变化时同步修正文、图和用例。拟采用方案与未核实行为必须明确标注，不能以设计图证明已经实现或验收通过。结果记入原主记录，不另建检查报告，不为本项检查强制给小任务建档。

对照最终任务 diff 和真实调用方，反查已记录的影响范围与验收入口是否覆盖全部受影响的功能及操作，尤其同页不同接口、历史数据源、下载/导出和共享组件旧入口。新增或缩小的影响同步更新；按场景关联验证版本与结果，未执行/未定位项不得记通过。非页面任务使用接口、定时任务、回调、命令、配置消费方或文档引用等实际入口。

## 证据对应版本

- 记录验证和审查针对的提交；有未提交改动时注明范围。测试读取整个工作区，不能把包含未提交依赖的结果宣称为某个 commit 单独通过。
- 跨会话恢复且 SHA 与范围不足以辨识未提交内容时，才记录差异指纹。指纹必须涵盖影响结果的暂存、未暂存和相关未跟踪文件，不能仅对 `git diff` 计算后声称覆盖全部内容。无法可靠比对就重新检查受影响部分。
- 提交、变更范围、配置、依赖或相关环境变化后，判断原证据哪些仍有效。相关变化需要补验和补审；无关文档变化不使所有测试失效。仅提交对象变化、实际内容未变时可复用已核实的结果。
- 例：A 版本测试通过后修改了相关实现，应报告“A 已验证，新增修改待验证”；待受影响检查完成再更新当前结论。
- 合入目标分支后按项目流程在合入结果上补核心验证；不把功能分支测试直接当作合入版本已通过。

## 完成与阻塞

实现完成、本地验证、测试环境验证、部署、运行态验收分别描述，并给出实际覆盖范围。相关路径尚未查清或未验证时保留该边界，不能因局部测试通过就宣称整个需求已完成。mock 测试不能证明真实接口有效，Pipeline 成功不能证明业务路径通过。

必要验证失败时先修复；无法继续则报告失败项和影响，不能提交失败状态或自动放行后续动作。只有用户明确接受限制且符合适用规则时才继续相关步骤，并在交付记录和最终汇报中保留限制。多个仓库或阶段部分完成时，逐项列明已完成、阻塞和未执行。
