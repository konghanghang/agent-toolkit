# 影响分析与实施

## 定向恢复和定位

已有任务记录先读目标、确认口径、实现与验证证据、下一步，再核对实际状态。需要补充需求原文或刷新冲突信息时才读取外部来源；区分需求事实、用户确认、文档描述与代码现状，不静默覆盖差异。

已知项目直接定位目标仓库，加载适用规则后按“已知文件或符号 → 相关模块 → 当前仓库”检索。项目不明时先查可用的项目索引或目录名；沿接口、依赖、消息或配置证据扩展到其他仓库，不默认扫描整个工作区。跨仓读取和修改分别按已有授权判断，不因找到关联仓库就扩大修改范围。

历史记录用于找线索，不能证明现行行为；知识和实现冲突时补证据，影响行为决策再澄清，不自动认定任一方正确。

## 核对已有能力与调用方

以下检查按改动适用性执行；文档、Skill 或配置维护可将入口理解为引用、触发方式或配置消费方，不虚构服务和接口。

- 先定位真实的同类接口、业务方法或交互，用现有对象和链路给出满足需求的最少必要变化。只有现有能力存在具体缺口时，才增加结构；不默认附带批量化、独立入口、进度持久化或轮询。更小的 diff 不能以改变已确认行为为代价。
- 编码前沿真实入口定位改动落点，核对数据何时就绪，以及现有赋值或转换循环、查询和配置来源能否复用；确需新增查询、参数、辅助类或调整执行顺序时，说明具体缺口与调用方影响。不要为减少局部改动行数或一次遍历增加整体复杂度。
- 区分需求目标、已明确的外部契约和文档中的实现建议。不能仅因需求写了“新增接口/字段”就直接新增；发现与现状冲突时，给出证据和必要调整建议，也不能擅自忽略已明确的契约。
- 从实际业务入口追踪本次受影响的数据路径：按需核对写入、转换或新旧同步、相关查询分支，直到调用方实际使用结果；参数或返回值变化时检查请求构造、响应解析及跨服务转发。范围限定在本需求的相关路径，不扩展成全系统审计；定位到类名、字段或搜索命中不等于已核实执行链。
- 新增或因风险考虑保留校验、查询、上下文传递前，核对输入来源、上游已提供的保证和下游实际用途，说明它防止什么具体错误。已核实的事实在同一任务后续方案中继续复用；证据不足先补必要追踪，不凭“可能需要”增加限制，也不因追求简化而删除真实授权、隔离或并发保护。


用简短的“已有能力、必要变化、调用方影响”说明方案，列出实际受影响仓库、模块和验收入口；服务发布、SQL、配置和数据修复仅在相关时说明。未查清且影响实现或验收结论的路径先补证据，不另建检查台账。

## 实施边界

- 修改前核对真实路径、工作区改动、当前分支和适用基线；按项目策略决定是否创建分支。已有任务分支先核对，不重复创建；不能安全切换时保留现场并说明阻塞，不擅自迁移或清理已有改动。
- 控制本次差异范围，不顺手重排、格式化或重构无关内容。优先修源头；跨仓修改超出授权时说明必要范围，不在当前仓库增加规避边界的补丁。
- 在已有分层和链路上实现必要差异。新增查询、参数、抽象或执行顺序调整须有具体缺口；不以更小 diff 为由改变已确认契约、权限、隔离和并发保护。
- 复用现有枚举、常量和配置来源，遵循项目布局与注释约定。调整非显而易见的业务规则、兼容行为或边界转换时同步说明原因，避免注释与实现矛盾。
- 实现改变影响范围时反查调用方和验收入口；需要新增行为决策或扩大授权范围时先澄清，纯内部实现调整自主完成。
