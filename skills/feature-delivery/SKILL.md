# 通用开发流程

从当前任务和已有授权继续，按复杂度与风险选择必要步骤。已获实施授权的小改动可直接核对、修改、验证并汇报，不强制计划、建档或完整发布链。

## 先确定适用规则

先读取目标仓库及目录的适用规则，确认项目或公司是否提供交付扩展。存在扩展时，在执行对应阶段前加载其前置条件、完成标准和记录要求，与本流程共同执行；不先跑完通用流程再补公司步骤，也不重复执行已完成的阶段。扩展明确限定的业务仓库规则不外推到工具箱或个人仓库。

本流程可独立运行，不依赖公司工具、凭证、固定知识库、分支名称或发布平台。项目决定实际构建命令、基线、分支策略和记录位置；不能从目录名或历史习惯猜测。适用要求之间存在影响执行的真实冲突时，先说明具体冲突并澄清。

## 从当前阶段继续

| 阶段 | 必要动作与完成条件 |
|---|---|
| 恢复上下文 | 沿用当前目标、确认范围和授权；已有任务记录先读，再核对与下一步相关的真实文件、Git 或环境状态。记录缺失不代表从未实施，不机械重做已有探索。 |
| 核对现状与影响 | 按 [影响分析与实施](references/implementation.md) 定向定位实际入口、已有能力和调用方，给出必要变化及验收入口。简单文档或配置调整只核对相关内容及引用。 |
| 必要澄清 | 仅对影响行为、兼容性、范围或验收的未决问题使用 [grilling](../grilling/SKILL.md) 的交付澄清；稳定术语与必要决策按需使用 `domain-modeling`。已确认内容不重问，内部实现选择不逐项审批；结束后按下述授权规则返回原任务。 |
| 实施 | 仅在已有实施授权后进入实施准备，完成适用扩展的基线等前置要求，核对工作区和已有改动；按已授权且已确认的范围实施，不机械新建分支或 worktree。 |
| 验证与审查 | 按 [验证与审查](references/verification.md) 检查完整任务差异及关键回归，复用有效结果。单独审查请求完成审查即交付，不自动进入修改阶段。 |
| 交付结果 | 说明实际改动、对应版本与验证结果、限制及剩余事项。需要提交时使用可用的 `git-commit`；其他交付动作按项目流程和已有授权推进。 |

专项技能可用且相关时直接复用；缺失时使用已有可用能力完成有依据的工作，并说明无法完成的部分，不声称已执行。纯分析只交付分析，用户已要求实施且范围明确时连续推进，不在每个阶段结束时等待确认。

## 授权、记录与完成

- 必要澄清结束后或无须澄清时，按用户原任务和已有授权继续：仅要求分析或方案时，汇总后结束本轮；已要求实施时，在已确认范围内继续。接受推荐方案、没有未决问题或记录进入“待开发”，均不能单独作为实施授权依据。
- 已获实施授权的开发任务默认做到实现、本地验证、审查和结果汇报；提交、推送、合并、部署和数据库写入分别依据明确授权。已有效授权不重复询问，确认业务口径或阅读流程不扩大操作授权。
- 按 [任务记录](references/task-record.md) 维护恢复所需的最少信息；已有主记录及时更新，小任务留在对话，不强制文件套件。
- 必要验证失败先修复或报告具体阻塞；能独立完成的工作继续，不覆盖用户现场。多仓任务分别报告完成、失败及未执行项。
- 到达用户要求的终点即汇报。需要额外授权才能继续时，先完成已授权且必要的准备，提供可审阅结果，再提出具体授权问题。
