# 需求澄清

围绕当前方案，把会影响实现或验收的业务边界问清楚。本技能只问人和确认口径，不改代码、不拉分支、不写 TAPD。

需要维护稳定术语或架构决策时，同时使用 `domain-modeling`。

## 何时使用

输入可以来自当前对话、需求文档、代码或 TAPD。仅当需求来自 TAPD 时使用 `tapd-story`；不要求其他任务提供 TAPD ID。先依据已有事实分析影响范围，出现以下情况才进入本技能：

- 用户明确说「澄清」「把边界问清楚」「grill」
- 方案会改变外部行为、状态语义、兼容性或多仓范围，且这些口径还没确认

不要使用本技能：

- 只是查看 TAPD
- 范围已经清楚，并且用户已下令改
- 机械改名、透传、补权限 SQL 这类不改业务语义的改动
- 确认从哪个 release 拉分支；那是目标项目交付流程的基线确认，不是业务边界问题

## 规则

围绕方案的每个未确认分支往下问，直到达成共同理解。一次只问一个问题，并附上推荐答案。问完必须等待反馈后再问下一个。一次问多个问题会让人失去方向。

如果某个问题可以通过探索 codebase 或已读取的 TAPD 正文回答，就去查证据，而不是问用户。仓库、模块、发布服务、是否需要 SQL，优先从代码、配置和目标项目规则得出，不要用本技能替代影响分析。

本技能只处理会改变结论的口径，例如：

- 用户可见行为到底变什么、不变什么
- 状态、类型、成功/失败判定
- 兼容范围和明确不处理的边界
- 跨仓时各仓各自负责什么

存在会改变结论的未决业务口径时，先解决这些问题。只要求讨论或方案时，澄清后交付已确认范围和剩余问题，不自动开始开发。用户已要求实施且口径明确时，按目标项目流程继续已授权工作，不再索要重复确认；确认业务口径不新增提交、推送或部署授权。

仅在 work 工作区需要衔接交付流程时，读取 [work 工作区约定](../tapd-story/references/work-context.md)。
