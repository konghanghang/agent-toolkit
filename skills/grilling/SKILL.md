# 澄清

本技能有两种互斥用法。先判断用法，再提问。不要把两种用法混在一次追问里。

需要维护稳定术语或架构决策时，同时使用 `domain-modeling`。用户未要求落盘时，术语和决策留在对话里，不为此建文件。

## 先判断用法

先独立判断是否有需要用户决定的未决口径，以及是否已有实施授权。前者决定是否需要交付澄清，后者决定澄清结束后能否实施。不能因无须澄清而推定允许实施，也不能因用户回答了澄清问题而推定新增实施授权。

由交付流程调用时，检查目标、用户可见行为、兼容范围和验收标准是否明确；继续任务先恢复已确认口径，只检查本轮新增、变化或冲突。无未决口径时简短说明已确认范围并返回调用方，不为完成阶段强造问题或固定轮数。

**访谈。** 用户明确要求 grill、grill me，或把一个尚未定下来的想法、方案、决策问透，而且当前不是交付流程里的口径确认。话题不限于软件，也不要求已有方案、仓库或 TAPD。不写文件，不建需求编号、主记录或 TAPD，不改代码，不开始实现。问到没有剩下的未决分支，也没有还没说出口的假设。汇总后等用户确认已经达成共同理解，在此之前不动手。

**交付澄清。** 由交付流程调用，或用户要在编码前确认业务边界。只问会改变结论的口径。必要问题问完就结束，不要为了把决策树问空而继续。用户只要求讨论时，交付已确认范围和剩余问题，不开始开发。用户已要求实施且口径明确时，回到调用方继续已授权工作，不再索要一次共同理解确认。确认口径不新增实施、提交、推送或部署授权。

已经在做某个具体改动时，用户只说「澄清」或「把边界问清楚」，走交付澄清，不要升级成访谈。只有用户明确要问透一个想法时才走访谈。

不要使用本技能：

- 只是查看 TAPD
- 没有需要用户决定的未决口径，且用户未要求访谈或澄清；是否实施另按原任务和已有授权判断
- 机械改名、透传、补权限 SQL 这类不改业务语义的改动
- 确认从哪个 release 拉分支；那是目标项目交付流程的基线确认，不是业务边界问题

## 问法

两种用法共用下面的问法。一次只问一个问题，不要在同一轮抛出当前所有能问的问题。

把待决事项看成一棵决策树：每个决策挂着依赖它的后续决策。现在能问的，是前提已经确定的决策。还依赖另一个尚未回答的问题的，放到后面。

先在内部整理当前能问的决策，告诉用户还剩多少个；暂时无法确定总数时写「预计 N 个」。用「第 i/N 问」标明进度。每题给出推荐答案，并把题目写成用户回答「对」就等于接受本题推荐口径；该回答不自动授权开始实施。然后等待。

用户的回答会改这棵树。已决决策会放出新问题，也会让原定问题作废。作废的跳过，并更新剩余数量。只有新证据暴露了会影响结论的未决问题时才追加，并先说明原因和调整后的总数。不要悄悄加问题，也不要为了凑数量继续问。

事实由本技能查，不要问用户。仓库、模块、发布服务、是否需要 SQL，以及代码或已读取材料里已经有的行为，去代码、配置、任务记录和需求正文里查。范围较大时用只读探索。查证还没结束时，只推迟依赖该事实的问题，不挡住其他已经能问的问题。决策仍然要问用户，并等待回答。

已明确的范围和口径直接沿用。用户选择沿用现有逻辑或排除某条方案后，不继续围绕已排除的分支追问。只有新证据确实影响已确认结论时，才说明原因后重新讨论。不能在追问过程中逐步扩大范围。

必须先看到成品或运行结果才能判断的问题，停止猜问，按 [处理不确定性](../feature-delivery/references/implementation.md#处理不确定性) 区分可查证事实、可实验问题和用户取舍。将需要实验或原型的问题交回调用方，按已有授权处理；访谈和交付澄清本身不新增实施或实验写入授权。材料就绪后只追问仍需用户决定的取舍，不让用户猜运行结果，也不以测量替代体验偏好。

## 访谈

从还没定下来的想法开始，不要求用户先写出完整方案。

每一答之后重算决策树。结束条件是当前能问的决策已经空了：每条分支都走过，没有剩下的悄悄假设。然后汇总已确认的决策和仍然无法靠讨论决定的点，等用户确认共同理解。共同理解确认只结束访谈，不自动授权实施；后续按用户原任务和已有授权处理，未获实施授权不改文件、不进入实施准备。

## 交付澄清

输入可以来自当前对话、需求文档、代码或 TAPD。仅当需求来自 TAPD 时使用 `tapd-story`；不要求其他任务提供 TAPD ID。先依据已有事实分析影响范围，再进入追问。本用法确认并记录口径，不改业务代码、不拉分支、不写 TAPD。

先读取已有任务记录中的确认口径、依据和未决项，再确认复用哪条现有流程、哪些行为保持不变，只问必须决定的行为冲突。

用户回答一个影响行为、范围或验收的关键问题后，已有主记录的，在进入下一问前更新对应确认项，记录结论、来源/日期和适用边界；只保存收敛结果，不抄聊天流水。尚无主记录且用户仅要求在对话中澄清时，沿对话保留已确认口径，并在结束时汇总；不因问答轮数或后续可能复用就自动创建需求编号、主记录或 TAPD。明确进入正式交付且确需建档时，再按项目记录规则确定归属和编号来源。

只处理会改变结论的口径，例如：

- 用户可见行为到底变什么、不变什么
- 状态、类型、成功/失败判定
- 兼容范围和明确不处理的边界
- 跨仓时各仓各自负责什么

不要用本用法替代影响分析。内部实现选择不在这里逐项审批。

必要问题全部解决后，已有主记录的核对记录，无主记录的在对话中汇总结论；简短说明已确认范围、排除项、验收标准、剩余待验证事项和下一阶段，明确告知澄清结束。新回答需要代码或运行证据时，先回到定向探索，再问仍需用户决定的事项。随后返回原任务：只要求讨论时交付方案；已有创建需求或实施授权时，由调用方在相应前置条件满足后继续，不重复索要已有授权或共同理解确认。认可方案不新增创建需求或开发授权，创建需求成功也不自动授权开发。

仅在 work 工作区需要衔接交付流程时，读取 [work 工作区约定](../tapd-story/references/work-context.md)。
