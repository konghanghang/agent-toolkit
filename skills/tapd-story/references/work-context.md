# work 工作区衔接

仅在任务属于 work 工作区时读取；通用需求分析、澄清和领域建模不依赖本文件中的路径。

## 交付流程

需要开发或继续交付时，由 [work-feature-delivery](../../work-feature-delivery/SKILL.md) 衔接已授权阶段；只看需求、澄清或记录术语时不进入完整交付流程。

本机权威流程为 `~/data/work/docs/reference/feature-fix-delivery-workflow.md`。先读取目标仓库适用的协作规则，再按任务阶段读取流程；文件不存在时采用目标项目现有规则，不猜测 release 或交付约定。

- 影响分析按第 1 节确认仓库、模块、服务和验证点，以代码、配置或用户明确说明为依据。
- 未决业务语义由 `grilling` 澄清；release 基线确认仍按第 2 节处理。
- 只要求分析或方案时，交付结果后结束。已要求实施且范围明确时，按第 2 节及后续阶段继续已授权工作，不重复确认已有口径。
- 提交、推送、合并、部署及数据库执行按已有授权分别处理；业务确认不扩大操作授权。
- 保留当前仓库开发、基线与发布批次独立判断、按需求提测和按批次上线的约定，不引入默认 worktree 或 amend。

## 知识文档

知识库位于 `~/data/work/docs/customer-service-knowledge-base/`。写入前读取该目录适用的协作规则，沿用现有文件及模板：

| 内容 | 目录 |
|---|---|
| 后续需要复用的稳定业务术语 | `glossary/`，遵守 `templates/knowledge.md` frontmatter |
| 现行系统边界和已实施架构事实 | `systems/` |
| 尚未落地的跨仓库方案决策 | `plans/` |

临时叫法留在对话；用户未要求记录长期知识时，不为完成流程而建文件。不要把术语或 ADR 复制到提测、上线清单。修改、提交和推送遵守对应仓库规则与已有授权。
