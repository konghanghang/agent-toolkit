# TAPD HTML 描述规范

## 允许标签

只使用：

```text
h3 p ul ol li strong code table thead tbody tr th td br a
```

表格单元格只允许 `colspan` 和 `rowspan` 属性；`a` 只允许 HTTP/HTTPS `href`。禁止 `style`、事件属性、脚本、iframe 和任意嵌入内容。

## 信息层级

- 需求草稿默认面向产品、开发和测试共同阅读，只保留帮助三方理解需求和预期结果的信息。
- 用户只要求“需求草稿”时，不自动写成实施方案；类名、方法名、注解、配置项、框架处理、内部异常实现和完整调用链默认不进入正文。
- 接口类需求可以保留外部契约，包括接口地址、请求方式、必要参数和外部响应行为，但不要展开内部转发、序列化或代码组织方式。
- 非目标和排除项只在能够防止范围误解时保留，不机械罗列所有不修改内容。
- 只有用户明确要求实施计划、开发方案或代码上下文时，才增加实现事实、代码位置、影响服务、技术风险和验证方式。

## 章节原则

- 大章使用 `h3`，明细直接使用短段落、列表或表格；不要为了表现层级增加无必要的标题。
- 不固定章节名称和数量，也不为凑模板创建空章。普通需求通常 1~3 个大章即可，只有内容确实独立时才增加。
- 每个章节只提供新的必要信息，同一背景、规则或预期结果只写一次。
- 正文必须能判断需要改变什么以及预期结果，但不强制单独设置“验收标准”章节。

## 推荐结构

### 普通单需求（默认）

以 **需求说明** 为核心，直接写清要改变的业务行为和预期结果。按需补充：

- **背景**：只有缺少原因会影响理解时添加，通常 1~2 句话
- **影响范围**：存在兼容要求、明确排除项或跨系统影响时添加
- **验收标准**：需求说明不足以直接判断完成，或存在多路径、边界、兼容和口径差异时添加

需求说明已经包含明确的输入、行为和预期结果时，不再用验收标准重复一遍。

### 缺陷修复 / 口径修正类需求

- 标题优先问题导向，例如：`【接口优化】修正xxx误记为yyy`
- 在需求说明中直接写清错误行为和目标行为
- 只有存在多入口、多状态或多条路径差异时才使用对比表；简单问题使用短段落或列表
- 无法从需求说明直接判断修正结果时，再补充必要的验收条件

### 接口类需求补充

- 在需求说明中写清外部接口范围、必要入参、响应和兼容行为
- 不在需求正文展开内部调用链、类名、方法名

### 父需求

- 写清总体目标和阶段范围
- 背景仅在有助于理解拆分原因时添加
- 总体完成条件仅在各子任务无法共同说明时添加

### 子任务

- 写清阶段目标和关键任务
- 覆盖范围、前置依赖和完成条件按实际需要添加

### 用户明确要求实施计划时

- 背景
- 目标与非目标
- 当前事实
- 方案设计
- 影响范围
- 验证方式
- 落地后文档处理

## 写法约束

- 段落短，列表清楚；不要把 Markdown 原文直接塞入 TAPD，也不要用一个长段落承载全部内容。
- 表格只用于确有多路径、多状态或多角色需要对比的场景；简单需求优先短段落或列表。
- 风险点仅在真实存在且会影响实施或验收时补充，不为凑结构创建空章节。
- 生成草稿后自检：
  1. 每个章节是否都增加了必要信息
  2. 是否能够判断要改变什么以及预期结果
  3. 是否存在可以删除的重复说明或空章节
  4. 是否误写成技术方案
