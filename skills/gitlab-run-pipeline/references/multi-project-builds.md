# 多项目构建：按产物依赖放行

## 先确定依赖，不预锁整批提交

开始前确定本轮项目、ref、环境、模块、额外变量和真实代码构建依赖。使用当前 POM、包依赖及 CI 构建/发布命令判断；不要按业务调用方向猜依赖，也不要套用固定的五仓库顺序。

- 下游编译需要上游本轮新发布的 API/client/npm 等产物时才建立依赖边。
- 区分仓库的泛化依赖与本轮变化需要的构建先后。仓库互相引用旧版本产物，不自动等于本轮必须循环构建；若确实要先发布某个 API，按实际可用的构建模块拆分。无法确认依赖时先查证，不虚构顺序。
- 没有代码构建依赖的项目可以一起触发，例如不消费后端 Maven 产物的独立前端。不为了等待后端部署而延迟其构建；若前端构建确实消费后端生成的接口产物，则按事实建立依赖。
- 同一批只冻结授权范围，不提前固定所有 SHA。项目轮到触发时才 inspect，取得已授权 ref 的最新提交。后来合入该 ref 的内容会随这一次触发构建。

## 产物阶段通过即可放行

默认检查 `build_artifacts` 阶段，前提是已核实该阶段**成功时，依赖包已发布到下游能访问的仓库**。

- Maven 模板执行 `deploy`（不仅是 `package` 或本地 `install`）通常满足发布条件，仍需确认对应环境的仓库配置。
- 若产物实际在另一个阶段发布，使用真实的发布阶段；仅上传 GitLab artifact 但下游不读取它，不等于 Maven 依赖可用。
- `SUB_MODULE` 是否限制 Maven reactor，要看公共模板的真实命令，不能只看变量名。

查询已记录的 Pipeline ID：

```bash
gitlab result --project group/upstream --pipeline-id 12345
```

响应示例：

```json
{
  "outcome": "in_progress",
  "job_summary": {"truncated": false},
  "stage_summary": {
    "build_artifacts": {"total": 2, "counts": {"success": 2}, "all_success": true},
    "deploy": {"total": 1, "counts": {"running": 1}, "all_success": false}
  }
}
```

`result` 可能因后续部署失败返回非零退出码，但仍输出完整 JSON；先读取阶段结果，不要仅按进程退出码判断产物是否已发布。

在产物发布契约已核实的前提下，`stage_summary.build_artifacts.all_success == true` 即可放行依赖它的下游，不等镜像、部署或通知结束。

阶段不存在、任务尚未完整返回、`job_summary.truncated == true`，或阶段内有 `pending/running/manual/failed/canceled/skipped/unknown` 等非成功任务时，不放行。普通 job 与 bridge 都计入汇总；bridge 自身成功还不够，关联下游流水线也须成功，状态缺失时不放行。任一列表查询失败不得当作空列表。允许失败的构建任务失败也不能当作依赖发布成功；空阶段不算成功。工具查询只包含该流水线实际加入的任务，不递归审查子流水线的产物发布 job；仍需核验发布契约及所需任务是否存在。

## 编排步骤

1. 建立本轮执行表：项目、授权参数、上游依赖、实际产物发布阶段、Pipeline ID、实际 SHA、产物是否就绪、最终状态。初始未触发、产物未就绪。
2. 对所有尚未触发且上游产物已就绪的项目（包括无依赖项目），各自执行 JIT inspect → trigger，使用 `--no-wait` 获取 ID。独立项目并行触发；每项目只创建一次，不依赖 shell 启动顺序假装依赖已满足。
3. 每轮按 Pipeline ID 查询所有正在运行的项目，默认间隔 15 秒，不逐个使用 `--wait` 阻塞调度。父流水线已终态，但产物阶段的 bridge 关联子流水线仍运行时，也继续轮询该父 ID 以刷新 bridge 状态；沿用本项目原监控超时，不重置计时。
4. 某个产物阶段成功后立即标记就绪，触发新满足条件的下游；同时继续监控上游剩余阶段。
5. 直到已触发流水线及影响产物放行的 bridge 关联子流水线全部终态，或明确需要人工操作/监控超时；未触发项目逐个报告阻塞原因。子流水线状态缺失时报告无法确认，不无限等待。

批量触发示例（参数已获得授权，计划来自该项目即将触发时的 inspect）：

```bash
gitlab trigger --project group/upstream --ref test --env test --module core \
  --plan-id '<该项目刚生成的plan_id>' --confirm --no-wait
```

`--no-wait` 只是把监控交给批量编排，不改变“持续等最终结果”的用户目标。不需要为了内部使用该参数再次向用户申请“不等待”的授权。

## 不追赶已触发后的新提交

以 GitLab 创建流水线时绑定的实际 SHA 作为本次执行记录。已经触发或产物阶段已放行后，上游 ref 再推进，**不回头检查、不补构建、不重启下游**。新提交留给下一轮。只有用户另行要求重建时才创建新的批次。

不要把最终检查各 ref 最新 SHA、自动补构建或循环追赶加入默认流程；最终汇报的是本轮实际构建的提交。

## 失败只影响相关依赖

- 产物构建/发布失败：不触发依赖它的下游；其他无关分支继续构建。没有成功发布依赖不能靠 `allow_failure` 放行。
- 产物已发布，但镜像/部署/通知失败或等待人工操作：产物仍可供下游使用，已启动下游继续运行，不自动取消；对应上游最终结果如实记为失败/需人工。
- 某个项目触发被 CI 规则拒绝或计划检查未通过：该项目没有成功构建，不放行依赖它的下游，其他独立项目不因此停止。
- 查询结果缺失、截断或超时：不推断尚未确认的产物阶段已成功；保留已经确认并记录的产物发布事实，不自动重跑。
- 不自动重试失败流水线或执行 manual job。报告失败任务 URL 和结构化原因，并继续监控其他已启动流水线。

例如 A 发布的 API 被 B、C 使用，D 没有构建依赖：A、D 可以同时启动；A 的产物阶段通过后 B、C 可以一起启动，不必等 A 的部署。A 后续部署失败仍需报告，但不自动停止 B、C、D。
