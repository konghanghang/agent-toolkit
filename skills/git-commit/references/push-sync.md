# 推送同步与受控 rebase

只有 push 授权已明确，且目标分支需要同步或提交发布状态需要核实时读取。主流程的四阶段推送不重做本地提交检查；当前任务有效的身份、审查与验证证据继续复用。

## 目标与远端新鲜度

已确认的 remote／branch 直接沿用。存在 upstream 时使用其真实 remote 和 ref；与 push 目标不同时始终检查用户授权的实际目标，不用 upstream 代替。没有 upstream 是正常情况，只有 push 目标不明时才询问，不为推送自动设置 upstream。

引用 `@{upstream}` 在 Bash、Zsh、PowerShell 中均保持完整单引号参数。下面是目标等于 upstream 时的一次只读预检示例：

```powershell
git status --short --branch
git rev-list --left-right --count '@{upstream}...HEAD'
git log '@{upstream}..HEAD' --format='%h %an <%ae> | %cn <%ce> | %s'
```

此检查必须基于刚完成的 fetch。没有 upstream 或目标不同时，用已确认的 `origin/main` 等实际跟踪引用替换上例，不运行必然失败的 upstream 命令。分支名称用于命令前需按当前 Shell 安全引用。

独立 fetch 对应 remote，例如：

```bash
git fetch origin
```

检查分叉前刷新目标引用；自动 rebase 的未发布判定还需刷新相关发布分支。fetch refspec 若只覆盖单一分支，应补齐可能发布本地提交的相关分支引用；存在其他发布远端时也需核实，未能确认不自动 rebase。不把一次单分支 fetch 当作所有远端分支均已核实。

本地缺少目标 tracking ref 时，只读核对远端分支是否实际存在；已确认不存在才按远端新分支处理，核对准备推送的全部提交及身份，不虚构远端身份基线。

fetch 失败停止推送。GitHub `GH007` 或其他身份拒绝同样停止，不关闭邮箱隐私保护、不在本流程内重签已发布提交。

## 无分叉的同步

- 远端独有 `0`：核对待推送提交的来源、范围和身份后普通推送；双方均为 `0` 时报告已同步。
- 只有远端有新提交：无异常 Git 操作、工作区干净时 fast-forward；例如已确认目标为 `origin/main` 时独立执行 `git merge --ff-only origin/main`。不自动 stash 或覆盖未提交内容，失败保留现场。
- 普通 push 可保留无关且不冲突的未提交文件；fast-forward 和 rebase 会更新工作树，必须先满足其干净条件。

## 分叉时的自动同步条件

推送授权只包含以下条件全部满足时的一次 rebase，不包含任意历史整理：

1. 用户已要求 push，且没有禁止 rebase；适用项目规则允许该同步方式。需要保留 merge 关系的集成／发布分支（例如 test／release）不默认 rebase；分支角色依据项目规则和当前交付任务判断，不能只按名称猜。
2. 工作区干净、没有未完成的 Git 操作；不自动 stash、清理或暂存其他改动来制造干净状态。
3. 记录原 HEAD、目标远端 tip 和共同基点；待重写整个区间（如 `origin/main..HEAD`）全部为本人普通提交，无 merge 提交或来源不明提交。不能仅按作者名字相同判断本人，结合有效身份及任务提交记录核实。
4. 待重写提交有可靠未发布证据：结合本次实际创建／推送记录及刷新后的相关远端引用，逐提交检查包含关系。`git branch -r --contains <sha>` 可发现当前分支之外的已发布记录；“功能分支没有 push”“无 upstream”或只查目标分支都不足以证明未发布。涉及已发布 Tag，或相关标签发布状态无法核实时也停止。
5. 所有待重写提交的签名约定一致，并具备相应签名能力；混合签名或策略不明确时停止。身份与签名细节见 [身份、隐私与签名](identity-and-signing.md)。

任一提交已被相关远端分支／已发布 Tag 包含、属于他人、具有 merge 关系或发布状态不明时，说明具体提交与原因，不重写、不强推。只有明确授权保留双方历史的 merge 场景才走后述例外；不把 rebase 不满足条件自动变成 merge 授权。

## 执行、核对与继续

满足全部条件后，按原签名约定独立执行一次普通 rebase。以下命令只针对已经核实的 `origin/main` 示例，不能代替上述条件检查：

全部待重写提交已签名：

```bash
git rebase --gpg-sign origin/main
```

全部待重写提交未签名：

```bash
git rebase --no-gpg-sign origin/main
```

不使用 interactive rebase、`--rebase-merges`、`--root`、`--onto` 或自动 amend 扩大重写范围。提交消息、Author 与关键改动应保留，Committer 使用已核对的当前身份，SHA 变化需更新实际交付记录。

冲突、签名错误或其他失败立即停止，报告当前 rebase 状态。不得自动 `--skip`、`--abort`、重复 rebase 或在冲突未解决时 push；用户明确要求处理冲突后才继续相应操作。

无冲突完成后在一次只读检查中核对：

- 对比重写前后的提交系列与最终树／差异，确认没有丢失或混入改动；可用 `git range-diff` 比较已记录的旧基点／HEAD 与新基点／HEAD。发现提交被自动省略时，核实是否已被上游等价包含，不能只看命令退出码。
- 每个重写提交的 Author、Committer、消息及 `gpgsig` 符合原策略；检查全部重写提交，不只检查最新 HEAD。异常不自动 amend 补救。
- 上游基线及依赖变化按影响补做验证。只有 SHA／签名等元数据变化、相关内容和环境未变时复用原结果，不把“自己的补丁没变”当成整体无须复验。

同步核对通过后重新 fetch 目标，检查远端独有提交数已为 `0`，再普通 push。重写未发布提交不需要强推。一次推送准备最多自动同步一次；远端再次推进或 push 因非快进被拒时，只读核对后报告，不无限追赶。

## 已授权保留合并历史的场景

同一任务已经明确授权将功能分支合入目标分支并 push，且合并前已同步远端、远端只在本地合并后推进时，可按已有授权普通 merge：先确认新增提交未改变交付范围或产生冲突，工作区干净，再独立 merge 对应远端分支，补验受影响内容。随后重新 fetch、核对远端独有数为 `0` 再推送。

单独 commit 或普通 push 不因此获得 merge 授权。出现冲突、影响不明、需要强推或与项目更严格规则冲突时停止；不将该例外用于绕过首次发现的 test／release 分叉。

## 推送与结果

显式指定真实 remote、branch；本地和目标分支同名时例如：

```bash
git push origin main
```

映射不同分支时使用已经明确授权的 refspec，不默认创建或切换其他分支。推送后一次只读检查状态、已确认的远端跟踪引用和待推送提交；没有 upstream 时仍使用该目标，不临时换成 upstream。跟踪引用核对失败时保留实际 push 输出，不把未知状态当作已同步。
