# Git 提交

按用户本次授权完成操作。默认先走下面的主流程；后续参考仅补充缺失证据或特殊场景，不再重复执行整套清单。适用项目规则更严格时优先遵守。

## 操作范围

| 用户要求 | 执行动作 |
| --- | --- |
| 检查、分析或拆分建议 | 只读检查，不提交 |
| 生成提交信息 | 只输出完整提交信息 |
| 准备提交 | 检查并暂存，等待提交指令 |
| 提交 | 完成本地提交，不自动 push |
| push／推送已有提交 | 直接进入推送流程，不重做提交预检或自动提交工作区改动 |
| 提交并推送 | 先完成本地提交，再进入推送流程 |

推送授权包含下述条件全部满足时对本人未发布提交的同步；用户明确禁止 rebase 时不执行。`amend`、已发布历史重写、强推及破坏性覆盖须另行明确授权，不属于例行操作。

## 本地提交：五个阶段

**默认不 fetch。** 本地 commit 不以远端最新、未落后或网络可用为前提；项目或用户明确要求先同步时再按其要求处理。未 fetch 的 tracking ref 只能表示缓存状态，不能报告为最新远端事实。

1. **一次本地预检。** 在同一次只读调用中确认仓库、分支／HEAD、工作区与 staged 范围、Git 操作状态，以及尚缺的身份、最近提交签名和项目规范。已审查的变更只核对状态与摘要；未审查内容、新增文件或实际变化只补读相关差异。无 upstream 是正常情况，不为 commit 查询或设置远端。
2. **一次显式暂存。** 独立执行 `git add <本次文件>`；不使用 `git add .`、`git add -A` 或 `git commit -a`。已有 staged 内容属于其他任务或来源不明时先停止，不擅自取消暂存。
3. **一次 staged 核对。** 在同一次只读调用执行 `git diff --cached --name-status` 和 `git diff --cached --check`。与已审查范围一致时不重读完整 diff；局部暂存、内容变化或边界不一致时补审对应差异。
4. **一次提交。** 独立执行 `git commit`，保留 hooks，按下述消息及签名约定执行。提交失败保留现场，不自动修改身份、关闭检查或 amend。
5. **一次提交后核对。** 在同一次只读调用检查新提交消息、文件范围、Author／Committer、实际签名及剩余改动。仅核对新提交，不再次扫描全部历史。hooks 改变内容或留下新改动时如实报告，不自动补交。

已审查、验证有效且边界明确的普通提交按这五个阶段完成，不为形式追加预检轮次。发现缺口就在相应阶段补齐，不另起一套“标准路径”。同阶段独立的只读命令合并调用，依赖前一步结果的操作保持顺序。

### 复用与验证

- 同一仓库、提交范围、相关内容及环境未变化时，复用当前任务有效的规则阅读、差异审查、身份和验证结论；暂存本身不使验证失效。不跨仓库盲目复用身份或签名策略。
- 规则文件、HEAD、身份配置或相关内容变化时，只补受影响的检查。配置来源、完整 remote 列表和较长历史仅在缺少证据或异常时展开。
- 使用项目已有验证入口；相关内容改变才按风险补测。测试读取整个工作区，依赖未提交文件时不能声称 staged 版本已独立通过；验证失败按项目规则处理，不默认为可提交。
- 一个提交表达一个完整目标。只有能独立使用、验证和回退时才拆分；不为展示效果临时改写文件、拆坏中间版本或改动已有历史。

### 身份与签名

需要补查时一次核对实际 `GIT_AUTHOR_IDENT`、`GIT_COMMITTER_IDENT` 和最近 HEAD 的 `gpgsig`，默认输出判断所需的摘要。身份异常不修改配置，先停止说明。

项目／用户无其他要求时：最近一笔提交带签名，本次也签名；最近一笔无签名，本次保持无签名。`commit.gpgsign` 和密钥配置不等于仓库签名惯例。按需读取 [身份、隐私与签名细节](references/identity-and-signing.md)，首次缺少证据、GitHub 邮箱异常、无历史仓库或签名不可用时使用。

### 提交信息

沿用项目语言、格式及 scope；没有规范时参考少量近期标题。标题只描述本次改动，简单提交只用一行；关键行为、兼容性或取舍需要解释时增加正文，多项内容逐行使用 `- `。

消息必须是真实换行。使用一个或两个 `-m` 参数，不创建临时提交消息文件，不使用 `-F`；安全引用参数，避免反引号、美元符号或命令替换被 Shell 执行。需要多行或 PowerShell 示例时读取 [提交消息与 Shell 引用](references/commit-message.md)。

## 推送：四个阶段

目标 remote、分支和提交范围已由本次授权及上下文确定时直接复用；只有目标确实不明时才补查或询问。普通 push 不要求清理无关且不冲突的工作区改动；需要改变工作树的同步须满足下述干净条件。

1. **刷新目标远端。** 独立 fetch 已确认的 remote；不要先重复一轮已知的 `status + branch + remote`。fetch 失败停止推送，不使用旧 tracking ref 冒充新状态。无 upstream 不猜目标；远端新分支须核实确实不存在。
2. **一次推送预检。** 合并检查当前分支／状态、目标、ahead／behind 和全部待推送提交的来源及身份；不重跑未失效的测试。按下表决定是否需要同步；只有发生分叉或需要同步时才读取 [推送同步与受控 rebase](references/push-sync.md)。
3. **普通推送。** 只有远端独有提交数为零且本地确有待推送提交时，独立执行显式目标的普通 `git push`。不使用裸 `git push`、强推或 `--force-with-lease`。
4. **一次结果核对。** 在同一次只读调用核对目标 ref、本地／tracking ref 同步状态和剩余改动。没有 upstream 时沿用已确认目标，不临时改用 `@{upstream}`。

| 远端独有 / 本地独有 | 默认处理 |
| --- | --- |
| `0 / 0` | 已同步，无须重复 push |
| `0 / N` | 核对后普通 push |
| `N / 0` | 工作区干净且无异常 Git 操作时以 `--ff-only` 同步；同步后无待推送内容就报告已同步 |
| `N / M` | 仅在下述条件全部满足时 rebase，否则停止说明具体缺口 |

自动 rebase 仅适用于：用户已授权 push 且未禁止同步；工作区干净；待重写的整个区间均为本人未发布、签名策略一致的普通提交；项目未要求保留该分支的 merge 关系。必须核对相关远端分支的包含关系及已知发布记录，不能只凭“功能分支没 push”或“没有 upstream”判断未发布。已发布／状态不明、他人提交、merge 提交或需要保留合并历史的 test／release 场景不自动 rebase。

符合条件时记录原 HEAD／基点，执行一次普通 rebase，按原签名约定处理并核对重写结果；基线或内容变化按影响补验，再刷新目标并重新完成推送预检。冲突保留现场并停止，不自动 skip、abort、amend 或 stash。远端持续推进时不循环追赶。具体判断、命令及已授权合并场景见同步参考。

## 停止条件与写操作隔离

- 未完成的 merge、rebase、cherry-pick、revert 或 bisect 阻止例行提交／同步；用户明确要求继续对应操作时按该操作处理，不把它当作普通新提交。
- 保留用户已有改动。不执行 `reset --hard`、强制 checkout、`clean`、自动 stash 或修改 Git 身份来完成例行操作；不提交凭证、产物、缓存及无关文件。
- 不跳过 hooks，不使用 `--no-verify`。发现 hook 未执行、签名失败或远端拒绝时报告真实结果，不静默降级或修改配置绕过。
- `add`、`commit`、`fetch`、同步（ff-only／rebase／已授权 merge）、`push` 分别独立执行，检查在后续只读调用中完成。不用 `&&`、`;` 或管道把写操作与检查捆成一条 Shell 命令；不扩大命令权限前缀绕过审批。
- 有效授权不重复询问；超出同步条件、提交边界不明或涉及已发布历史时才确认相应部分。技能授权边界不替代执行环境权限。

## 结果汇报

默认简短报告提交 ID／标题、实际操作及是否推送、剩余未提交改动。推送后说明同步结果。身份、签名及有效验证照常检查，只在异常、未验证边界、用户关心或项目规则要求时展开；没有 fetch 时明确区分本地 tracking 状态与最新远端状态。
