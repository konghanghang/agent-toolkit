# Git 提交

## 确认任务意图

先根据用户请求确定本次操作范围：

- 只要求检查或拆分时，只分析改动，不执行提交。
- 只要求生成提交信息时，只输出提交信息。
- 要求准备提交时，完成检查和暂存后等待确认。
- 明确要求提交时，完成必要检查后执行 `git commit`。
- 只有明确要求推送时才执行普通 `git push`。
- `amend`、`rebase`、强推和历史改写不属于本技能的执行范围，遇到这类请求时停止并作为独立任务处理。

## 选择执行路径

用户只要求推送、且不需要先创建新提交时，直接进入“推送前检查”，不要重跑提交检查和测试。

需要创建提交时默认优先走快速路径。只有不满足条件时才升级到标准路径，不要为了形式重复检查。

快速路径要求同时满足：

- 当前任务已经读过完整变更，并完成与风险相称的验证。
- 验证后文件内容没有变化；仅执行 `git add` 不算内容变化。
- 项目规则和提交边界已经明确；Git 身份、远端和签名惯例已有仍有效的证据，或能在第 1 步的同一次只读预检中确认。
- 没有来源不明的 staged 内容，也不处于 merge、rebase、cherry-pick、revert 或 bisect 流程。
- 不涉及身份修改、历史改写或其他高风险操作。

快速路径固定为五步：

1. 在一次只读检查中确认状态、变更摘要、提交范围、Git 操作状态，以及尚缺的身份、远端和签名证据；复用仍有效的规则和测试结果。
2. 独立执行一次显式 `git add <files>`。
3. 在一次只读检查中执行 staged 文件列表和 `git diff --cached --check`；提交边界没有变化时不重复全文阅读 diff。
4. 独立执行一次 `git commit`。
5. 在一次只读检查中核对状态、提交消息、提交文件范围和签名。

以下任一情况改走标准路径：仓库没有提交历史、尚未审查的用户改动、测试后又修改内容、Git 配置或远端出现异常，或快速预检无法确认安全边界。普通推送使用独立的推送流程，不因此升级到标准提交路径。

发现异常 Git 操作状态、来源不明的 staged 内容或无法可靠划定提交边界时，不进入标准路径，直接停止并说明阻塞项。

标准路径只补齐缺失或失效的证据；已经审查的 diff、已经通过且内容未变化的验证，以及仍有效的身份和签名结论都直接复用，不从头重做。

除非后一个检查依赖前一个检查的结果，否则把同一阶段的 `status`、`diff`、`config`、`log` 和 Git 操作状态等只读命令合并到一次 Shell 或工具调用中；不要把每条只读命令拆成一轮交互。

## 读取项目规则

1. 查找并读取当前目录范围内适用的项目协作和提交规范，例如 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、Git commit template 和 commitlint 配置；同一任务中未发生范围变化时只读一次。
2. 遵守当前运行环境的指令优先级和目录作用域。
3. 项目存在明确提交规范时优先遵守；没有明确规范时，参考最近的 Git 历史，沿用现有语言、格式和 scope 习惯。
4. 规则冲突且无法根据指令优先级解决时，停止并询问用户。

## 检查工作区

1. 确认当前目录位于 Git 仓库中。
2. 执行 `git status --short --branch`，分别识别暂存、未暂存和未跟踪文件。
3. 尚未审查改动或提交边界发生变化时，检查暂存区和工作区完整 diff，理解每项改动的实际语义；完整 diff 已经审查且边界未变化时，只确认状态和摘要，不重复全文阅读。
4. 确认是否处于 merge、rebase、cherry-pick、revert 或 bisect；一律停止普通提交。用户明确要求继续对应操作时，将其作为本技能之外的独立任务处理。
5. 保留用户已有改动。禁止执行 `git reset --hard`、`git checkout --`、`git clean` 或其他破坏性清理。
6. 发现与当前任务无关但不冲突的改动时，不回滚、不暂存；发现直接冲突或来源不明的异常改动时，停止并询问用户。

一旦确认异常 Git 操作状态、来源不明的 staged 内容或其他明确阻塞条件，立即停止；不要继续做身份检查、测试或提交信息生成。

## 预检 Git 身份与邮箱隐私

标准路径或快速路径缺少仍有效的身份、远端、签名证据时，检查实际生效的作者和提交者身份。将这些命令合并到该路径的首次只读调用中；当前任务中连续创建提交、且身份、远端和签名配置未变化时，复用首次结果，不为每个提交重复完整预检。

```bash
git config --show-origin --get user.name
git config --show-origin --get user.email
git config --show-origin --get commit.gpgsign
git config --show-origin --get user.signingkey
git var GIT_AUTHOR_IDENT
git var GIT_COMMITTER_IDENT
git remote -v
```

部分 `git config --get` 在配置未设置时会返回非零，这表示“使用默认值”，不等于预检失败。合并只读检查时不要使用 `&&` 或 `set -e` 让这类预期结果中断后续命令。

先判断仓库是否存在提交历史：

```bash
git rev-parse --verify HEAD
```

该命令在无提交历史的仓库中预期返回非零；根据结果进入无历史分支，不把它当作工具执行失败。

存在 `HEAD` 时，再检查最近一笔提交对象的签名状态：

```bash
git log -1 --format='%H'
git cat-file -p HEAD  # 检查最近一笔提交是否存在 gpgsig
```

如果存在上游分支，再检查最近已被远端接受的身份和所有尚未推送提交：

```bash
git log @{upstream} -1 --format='%an <%ae> | %cn <%ce>'
git log @{upstream}..HEAD --format='%h %an <%ae> | %cn <%ce> | %s'
```

执行时遵守以下规则：

1. 远端是 GitHub，且近期远端提交稳定使用同一个 `users.noreply.github.com` 地址，而当前仓库突然使用不同的私人邮箱时，将其视为高风险身份漂移；在提交前停止并向用户说明。
2. 不要仅凭“不是 noreply 地址”就断言配置错误；公开邮箱也可能是用户的明确选择。优先依据仓库历史和用户指令判断。
3. 普通提交任务中不修改 Git 身份；发现配置错误时停止并报告，不在本技能内修复既有提交。
4. 签名策略优先遵循用户明确要求和项目规则；没有明确要求时，以当前仓库最近一笔提交对象的实际 `gpgsig` 状态为准。
5. 最近一笔提交包含 `gpgsig` 时，本次提交也使用签名；如果 `commit.gpgsign=false`，显式执行 `git commit -S`。需要签名但未配置可用的 `user.signingkey` 时停止提交并说明原因，禁止静默降级为无签名提交。
6. 最近一笔提交不包含 `gpgsig` 时，本次提交保持无签名；如果 `commit.gpgsign=true`，显式使用 `git commit --no-gpg-sign`，但不要修改仓库级或全局签名配置。
7. `commit.gpgsign` 只表示 Git 的默认行为，`user.signingkey` 只表示本机具备签名能力；两者都不能单独用于推断仓库签名惯例。
8. 仓库没有任何提交历史时，优先遵循用户明确要求和项目规则；仍无法判断时先询问用户。
9. 没有上游分支时，先判断当前分支是否存在对应的 `origin/<branch>`；都不存在时只报告本地身份，不猜测远端身份惯例。

## 排除不应提交的内容

提交前检查并排除：

- `.env` 和本地配置
- 密钥、Token、密码、验证码、cookie 和 session
- 构建产物、缓存、日志和临时文件
- 与本次提交无关的格式化或重命名
- 用户未要求提交的其他工作区改动

禁止为了让提交变得干净而删除或覆盖这些文件。

## 拆分原子提交

1. 一个提交表达一个完整交付目标；同一目标的代码、测试、配置、文档和配套 Skill 默认放在一起。
2. 只有改动能够独立使用、独立验证和独立回滚，而且拆分边界清晰时才拆成多个提交。
3. 拆分需要临时改写共享文件、复杂局部暂存或重复验证时，默认保持一个完整提交；用户明确要求拆分时除外。
4. 纯格式化、纯重命名和明显无关的文档调整原则上单独提交。
5. 如果拆分导致中间提交无法编译、无法测试或行为不完整，保持为一个提交。
6. 已有暂存内容不属于当前提交时，禁止擅自取消暂存或混入新提交；先向用户说明。

## 执行必要验证

1. 根据项目规则和本次改动范围选择测试、编译、lint 或文档一致性检查。
2. 优先使用项目文档、现有脚本和 CI 中已经定义的验证入口，禁止猜测不存在的命令。
3. 当前任务中已成功验证、且之后文件内容未变化时直接复用结果；暂存操作本身不触发重复测试。
4. 验证后修改过内容时，只重跑受影响的检查；没有风险依据时不要机械重复整套测试。
5. 测试读取的是整个工作区，不是 Git 暂存区。相关未暂存或未跟踪内容可能影响结果时，不得声称 staged 提交已独立验证；应调整提交顺序或在提交形成后、暂存下一组内容前验证。
6. 验证失败时停止提交并报告失败原因，除非用户明确接受风险并且当前项目规则允许继续。
7. 无法执行验证时，明确说明未验证的项目和原因。

## 隔离 Git 元数据写操作

1. 将 `git add`、`git commit` 和 `git push` 分别作为独立的 Shell 或工具调用执行。
2. 禁止把上述写操作与 `git diff`、`git status`、`git log`、`git cat-file` 或其他检查命令通过 `&&`、`;`、管道等方式放在同一次调用中。
3. 写操作完成后，再在下一次调用中执行只读检查；不要为了合并调用而给只读 Git 命令增加沙箱外执行权限。
4. 需要越过 `.git` 只读保护时，依赖当前环境已经加载的精确命令 Rule；Rule 未加载或不匹配时按环境要求请求授权，不通过扩大命令前缀绕过。

## 暂存文件

1. 显式列出并暂存属于当前原子提交的文件。
2. 默认禁止使用 `git add .` 或 `git add -A`，避免夹带无关改动。
3. 同一文件同时包含相关和无关改动时，优先使用安全的局部暂存方式；拆分需要临时改写工作区或无法可靠复核时，保持一个提交或先询问用户。
4. 仅在独立调用中执行属于本次提交的暂存命令，例如：

```bash
git add README.md src/app.py
```

5. 暂存成功后，在另一次调用中执行：

```bash
git diff --cached --name-status
git diff --cached --check
```

6. staged 边界与已审查范围一致时不重复全文阅读；出现局部暂存、来源不明改动、权限变化、删除或边界变化时检查完整 staged diff。

## 生成提交信息

1. 优先使用当前项目明确规定的提交格式。
2. 项目没有明确规范时，参考最近的 commit subject，保持语言和结构一致。
3. 标题简短直接，只描述本次提交做了什么，不写背景、过程、评价或句号。
4. 简单且标题已能完整表达语义的提交，默认只使用一行标题，不为了形式强制添加正文。
5. 出现以下任一情况时，在标题下方增加提交正文：
   - 标题无法完整说明多项相关变更或关键行为变化；
   - 变更涉及重要业务规则、配置与默认值、数据迁移、API 或兼容性影响；
   - 实现中存在不易从 diff 直接看出的原因、取舍、约束或风险；
   - 项目提交模板、项目规范或用户明确要求提交正文。
6. 正文与标题之间留一个空行；正文包含两项及以上独立改动、行为变化或验证结果时，默认使用项目符号列表，每行以 `- ` 开头，不把多项内容压缩成一个长段落。
7. 只有正文表达单一原因、取舍、兼容性说明或风险时，才使用简短段落；项目已有明确正文风格时优先沿用项目风格。
8. 列表描述行为和影响，不简单罗列文件；每项只表达一个要点，避免重复标点，项目历史中的列表项不以句号结尾时保持不加句号。例如：

   ```text
   feat(api): 支持本地获取 OpenAPI AccessToken

   - 新增本地 AccessToken 接口，转发 cropId 和认证请求头到 SaaS
   - 保留上游响应状态、响应体及 X-Trace-Id
   - 保持现有业务鉴权行为不变
   ```

9. 提交消息中必须使用真实换行。禁止把字面量 `\n`、`\r\n` 或其他转义文本写入标题或正文来表示换行。
10. 多个提交应分别生成能够独立表达语义的标题，并分别判断是否需要正文。
11. 用户只要求“生成提交信息”时，最终回复只包含完整的提交信息本身，并保留真实换行和列表格式。
12. 仓库没有提交历史且项目没有规定格式时，根据本次任务生成简洁直接的标题，不执行依赖 `HEAD` 的历史风格检查。

## 执行提交

1. 只有用户明确要求提交，或者当前任务已经明确授权提交时，才能执行 `git commit`。
2. 只有一行标题时，可以使用 `git commit -m "<标题>"`。
3. 包含正文时，直接使用两个 `-m` 参数：第一个传标题，第二个传完整正文。正文必须作为一个命令参数传入，并在参数内部使用真实换行；禁止用字面量 `\n` 拼接多行内容。
4. 多项正文在第二个 `-m` 参数中连续书写，每项以 `- ` 开头。不要创建临时提交消息文件，不要使用 `git commit -F`。
5. 使用适合当前 shell 的安全引用方式，确保标题和正文各自只作为一个参数传给 Git；不要让正文中的反引号、美元符号、命令替换或引号被 shell 解释执行。
6. 严格执行预检确定的仓库签名惯例：需要签名时在命令中加入 `-S`；需要无签名且 `commit.gpgsign=true` 时加入 `--no-gpg-sign`。禁止为了单次提交修改仓库级或全局签名配置。
7. 将 `git commit` 作为独立调用执行，不在同一次调用中追加提交后检查命令。
8. 禁止执行 `git commit --amend`、rebase 或其他历史改写；相关需求脱离本技能单独处理。
9. 提交失败时保留现场，报告错误，不通过修改全局 Git 配置强行绕过。

多行正文命令示例：

```bash
git commit -S \
  -m 'feat(api): 支持本地获取 OpenAPI AccessToken' \
  -m '- 新增本地 AccessToken 接口，转发 cropId 和认证请求头到 SaaS
- 保留上游响应状态、响应体及 X-Trace-Id
- 保持现有业务鉴权行为不变'
```

## 推送前检查

用户明确要求推送时，在 `git push` 前执行：

```bash
git status --short --branch
```

存在上游分支时，再执行：

```bash
git rev-list --left-right --count @{upstream}...HEAD
git log @{upstream}..HEAD --format='%h %an <%ae> | %cn <%ce> | %s'
```

没有上游分支时，先确认目标 `<remote>/<branch>` 是否存在；存在则用它代替 `@{upstream}` 完成分叉和领先提交检查，不存在则明确报告“没有远端身份基线”，并检查准备推送的全部本地提交身份。不要直接执行必然失败的 `@{upstream}` 命令。

确认：

- 工作区状态符合预期；
- 分支没有意外落后或分叉；
- 所有领先提交的 Author 和 Committer 身份都符合仓库惯例；
- 没有私人邮箱、错误机器人身份或混入的其他用户提交；
- 推送目标和分支正确。

完成预检后，将普通推送作为独立调用执行，并显式传递远端与分支：

```bash
git push origin master
# 或
git push origin main
```

功能分支使用已经确认的真实远端和分支执行 `git push <remote> <branch>`。禁止使用依赖隐式上游解析的裸 `git push`，禁止把推送后检查拼接到同一次调用中。推送完成后，再单独检查分支同步状态和待推送提交列表；推送前没有上游时继续使用已经确认的 `<remote>/<branch>`，不要改用 `@{upstream}`。

如果推送返回 `GH007` 或其他身份错误，停止并报告；不要关闭 GitHub 邮箱隐私保护，也不要在本技能内 amend、rebase、重签或改写历史。

如果本机未配置 `gpg.ssh.allowedSignersFile`，`git log --show-signature` 或 `%G?` 可能无法在本地验证 SSH 签名。不要因此直接断言提交未签名；可以用 `git cat-file -p <commit>` 检查是否存在 `gpgsig` 字段，并明确区分“存在签名”和“本地已验证签名”。

## 提交后检查

提交完成后执行：

```bash
git status --short --branch
git show --stat --summary --format=fuller HEAD
git cat-file -p HEAD  # 确认 gpgsig 的存在或缺失符合预检确定的签名惯例
```

这些提交后检查必须在 `git commit` 已经单独完成后，通过一次新的只读调用执行；不要拆成多轮重复检查。

检查完整提交消息时确认：标题与正文之间只有预期空行，多项正文逐行以 `- ` 开头，消息中不存在用于表示换行的字面量 `\n` 或 `\r\n`。如果提交消息格式不正确，停止并报告；没有用户明确授权时不得自动 amend。

提交前已经检查过现有领先提交时，提交后只核对新提交的 Author 和 Committer；完整领先提交集合留到明确要求 push 时统一检查，不重复扫描。

向用户报告：

- commit ID 和标题
- 实际提交的文件范围
- 是否仍有未提交改动
- 当前分支是否领先远端
- Author 和 Committer 是否符合仓库身份惯例
- 新提交是否签名，以及是否符合当前仓库签名惯例
- 哪些验证已经完成，哪些未执行

除非用户明确要求，否则禁止执行 `git push`。
