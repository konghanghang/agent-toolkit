# 交付记录

通用记录原则、最小信息与更新方式见 [任务记录](../../feature-delivery/references/task-record.md)。以下补充工作环境的建档条件、知识库归属及交付证据。

## 何时落盘

- 单独 TAPD 管理按 [tapd-story 核心边界](../../tapd-story/SKILL.md#核心边界) 交付；已有本地记录可按需读取，是否写入仍由本轮目标和有效授权决定。
- 工作项目业务代码交付（功能、Fix、独立性能优化或重构等）一旦获得实施授权，无论改动大小，都必须维护需求主记录；单仓小改只裁剪正文和验证内容，不能以对话替代建档。类型、TAPD 与编号条件统一见 [交付规则 §1.3](delivery-workflow.md#13-入口收敛与正式建需)，入口不同不改变这些条件。
- 纯专项审查或提交按本轮范围处理，不因已有方案、代码或记录缺失而强制补 TAPD、重走开发或改写历史；工具箱及本地工具等非业务维护遵循通用流程。后续授权业务代码修改时再执行实施前检查。
- 用户只要求在对话中探索、分析或澄清，且尚无需求主记录时，在对话中汇总已确认口径与未决项；不因跨仓、多轮问答或形成稳定结论自动创建编号、TAPD 或需求主记录。已有主记录的写入仍按本轮目标和有效授权判断。
- 先区分独立规划与需求交付。用户仅要求保存计划或方案、尚未关联具体交付任务时，按知识库 `AGENTS.md` 的专项计划规则归档，不自动生成需求编号、交付状态或实施记录；计划中的拟操作不构成实施授权。
- 本轮明确要求建立或维护本地交付记录，或已有实施、提测等业务交付授权时，优先复用主记录；确需新建时先确认编号来源，再按知识库规则建档。仅要求保存分析或方案时，只落盘所要求的内容，不附带开发、测试或发布清单。
- 独立计划实际进入需求交付后，再建立或关联主记录，实施进度与验收证据只在主记录维护。单仓已有设计可保留并由主记录引用，不平行维护总进度。
- 写入前读取目标目录规则，核对本轮授权是否涵盖该仓库写入；计划公开到站点时只记录可公开给团队的内容。原始 TAPD、附件及完整日志留在临时交接目录，不搬入知识库。
- 测试计划与结果维护在需求主记录；上线物料与执行结果进入 `delivery/releases/<批次>.md`，由需求主记录引用，不重复完整开发记录。

## 实施前检查

在首个业务代码修改或委派 `implementer` 等角色实施前，主 Agent 先完成 [§1.3 的边界收敛检查](delivery-workflow.md#13-入口收敛与正式建需)，再完成以下检查；已有任务从当前阶段恢复，不重做已完成且仍有效的分析：

1. 读取知识库 `AGENTS.md` 和 `templates/requirement.md`，定向查找 `delivery/requirements/<需求或 Fix ID>/index.md` 及相关记录。已有主记录先恢复并更新本轮范围、已确认口径、当前状态和下一步，不另建重复目录。已有代码而无记录时，核对实际成果与证据后记录当前事实，不断言从未开发，也不回写虚假的开发或验证历史。
2. 确需新建时先按现有线索定向查找编号：有 TAPD 编号使用原编号，既有需求内的必要技术调整归原需求；仅已确认是 Bug Fix 且没有 TAPD 编号时使用稳定的 `fix-yyyyMMdd-简述`。独立非 Bug 业务代码交付须按 §1.3 取得真实 TAPD ID，创建授权或必要信息缺失时保留草稿并补齐缺口；不得冒用 `fix-` 或虚构本地编号。
3. 按模板建立最小主记录，保存来源、已确认范围与排除项、拟采用方案、影响范围与验收入口、当前阶段和下一步；已核对的仓库与版本据实填写，未知信息明确标注。简单 Fix 可用短文字和一行验收入口，不机械创建设计、测试等全套文件。
4. 核实主记录已经实际写入并可恢复，再修改业务代码或交接实现任务。知识库不可写、必需规则不可读或编号未定时，报告具体缺口，继续可独立进行的只读调查；不得先编码后补档。

记录进入“待开发”、建立主记录或写入拟操作，都不是实施或后续发布动作的授权；仍以用户指令及有效会话授权为准。

## 更新时机

在本轮已授权的业务交付或记录维护范围内，已有或已明确创建的主记录按通用任务记录规定的时机更新。work 将稳定探索结论、关键口径和阶段证据落盘作为正式需求探索、澄清和阶段交付的完成条件，不等编码或提测才补写：

- 一段探索形成稳定结论后、转入另一条独立链路前保存；用户确认关键口径后、进入下一问前更新确认项及来源/日期。
- 结束本轮或转入实现前，核对主记录、关联分析和“影响范围与验收入口”一致，写清下一步。
- 内容分类和拆分遵循知识库规则，临时报告不作为关键结论的唯一来源；需求完成后保留历史交付性质，追加调整复用同一目录并区分轮次。

已授权的业务开发交付在开发结束或本轮收尾前，还必须完成以下材料检查，不以用户是否要求提测、提交或合入 `test` 为触发条件：

- 对照实际改动更新处理方案、影响范围与验收入口、每仓版本及未提交范围、验证与审查结果、已执行的交付动作和剩余事项；失败、未执行与待确认分别记录。
- 盘点实际需要发布的服务，以及 SQL、配置、脚本等物料；无则明确写“无”，未核实不能写成无。发布批次沿用 [交付规则 §8.2](delivery-workflow.md#82-目标批次确认目录与命名)，与开发基线独立判断。
- 批次能确定时，按 [§8.5](delivery-workflow.md#85-生成与追加规则) 增量更新同批上线清单，保留其他需求的内容；主记录与批次清单双向链接，尚未提交、合入、推送、执行或验收的状态据实保留。
- 批次确有歧义时，在主记录保留物料类型、影响和权威来源或路径、批次待确认原因与下一动作；不编造日期或临时批次，不以此阻塞已授权且独立的开发。完整人工 SQL 仍只维护在确定后的实际批次清单，不在主记录复制另一份正文。
- 最终汇报给出实际更新的主记录路径及批次清单路径；批次待定时说明原因和已保存材料的位置。必需记录或材料缺失时，明确报告缺口，不能将实现完成表述为完整交付。

## 最小信息

1. 来源与范围：需求链接或用户说明、已确认行为、排除范围、菜单/功能级影响范围与验收入口；区分需用户决策的待确认项与需代码/环境核实的待验证项。
2. 处理方案：改动前后行为、主流程、关键规则、模块职责，以及关键决策及原因；按知识库规则配核心图，区分拟采用方案、已实现和待确认内容。
3. 每仓实现与验证：真实仓库标识与仓库内路径、基线 ref/SHA、功能分支、当前提交、未提交改动范围、验证命令与结果、审查覆盖版本和发现。
4. 实际交付：test 合入与推送、目标批次、release 合入与推送、Pipeline ID/实际 SHA、环境与运行态验收，各自独立记录。

尚不适用的项省略；需要但未执行的项写“未执行”并说明原因。未知写“待核对”，不根据功能分支基线推断批次，不根据 Pipeline 成功推断业务验收成功。计划里的操作历史不是新会话的授权凭证，授权以用户指令及仍有效的会话上下文为准。

## 简短示例

下面仅示意需要保留的信息；落盘使用知识库需求模板的章节，不再嵌套一份状态记录，按实际需求裁剪：

```markdown
## 交付记录

- 来源：需求链接；范围：新增查询条件，历史数据回填不在本轮
- 处理方案（拟采用）：原查询不支持该条件；新增可选筛选，由查询服务在原有权限范围内追加条件，返回符合条件的数据；不传时保持原行为。实现后核对并更新此处。
- 决策：复用原查询入口，保持调用方不传新参数时的兼容性；简单条件透传不另画图。
- 验收：有条件时按条件过滤；不传条件时保持原有查询行为
- 仓库：仓库标识与仓库内路径；基线：release 分支及 SHA；功能分支：实际分支
- 代码版本：当前 commit；未提交改动：无 / 本轮相关文件范围
- 验证：实际命令、结果及对应代码版本；真实环境验证未执行
- 审查：覆盖基线至当前版本的完整任务差异；结论及未解决项
- test：合入与推送分别记录；目标批次：已确认日期 / 待定
- release、Pipeline、运行态验收：按实际执行结果记录
- 关联材料：提测链接、批次上线清单链接
- 下一步：具体待办或阻塞
```

多仓时将“仓库、版本、验证、交付状态”按仓库分行，关键验收点只写一次。复杂验收可增加“验收点 → 实现位置 → 验证结果”的短表，无需穷举所有文件和测试。
