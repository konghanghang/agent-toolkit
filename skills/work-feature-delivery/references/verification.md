# 工作环境验证与审查补充

开发交付前复用 [通用验证与审查](../../feature-delivery/references/verification.md)，不另维护一套通用检查规则。工作环境额外要求：

- 按 [五类入口](stages.md#按当前材料选择入口) 核对本轮目标与实际阶段，已有成果及有效证据直接复用；纯专项审查或提交在其授权终点交付，不强制补 TAPD 或重走开发。新业务代码任务转入实施前，检查 [§1.3](delivery-workflow.md#13-入口收敛与正式建需) 的范围、排除项、验收、待验证项与授权，真实未决项一次一问，无未决项不追加形式确认。
- 首次合入 `test` 前确认拟合入版本已完成完整任务差异审查；同版本结果直接复用，只补新增或未覆盖部分。
- 合入 `test` 后按 [交付规则 §6](delivery-workflow.md#6-合并-test-与提测) 在合入结果上补核心验证，通过后才依授权推送。
- 业务代码交付的主记录须在首个业务代码修改或委派实现前按 [实施前检查](delivery-record.md#实施前检查) 实际建立或恢复更新，单仓小改不能免建档；独立非 Bug 技术交付须有真实 TAPD ID，不冒用 `fix-`，既有需求内必要技术调整复用原需求。开发交付时按知识库规则及模板核对处理方案正文、必要核心图、实际实现和测试预期；反查“影响范围与验收入口”，结果写回原主记录。
- 开发结束或本轮收尾前按 [记录与材料检查](delivery-record.md#更新时机) 核对发布服务、SQL、配置、脚本及真实版本状态；即使本轮未要求提测、提交或合入 `test` 也须检查。批次能确定时，需求主记录与同批上线清单双向链接；批次确有歧义时，主记录保存材料、待确认原因和下一动作，不虚构批次。
- 最终汇报给出实际更新的主记录路径、批次清单路径或待定原因，明确未执行、待验证与材料缺口；缺必需材料不能声称完整交付，文档准备不代表提测、部署或数据库执行已获授权或完成。
- 测试库核对按需使用 `verify-test-db`，浏览器验收按需使用 `local-browser-verify`；提测、部署与运行态验收分别记录，不将 Pipeline 成功视为业务验收通过。
