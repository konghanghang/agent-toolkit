# 验证与审查

## 按风险选择验证

- 优先从项目文档、CI 和已有脚本确定测试、编译、lint 命令，不猜命令。
- 业务行为变更和缺陷修复从已确认行为与相关数据分支选择测试，验证外部可观察结果和关键回归；不强制 TDD，也不逐个测试边界要求用户批准。拒绝或回退用例必须有业务契约或实际风险依据，不能仅因实现中新增了限制就把它当成正确预期。
- 接口契约变化时，验证已识别调用方的实际处理方式，尤其请求序列化、响应解析类型和结果使用。仅 Controller 或 Service 单测通过，不能证明跨服务兼容；未验证的调用方边界必须明确列出。
- 测试优先覆盖业务分支和兼容边界，不为测试数量增加重复用例。方案收敛后同步清理只验证实现细节或已撤销方案的测试，保留仍有效的业务约束。
- 文档、机械调整等低风险改动使用对应校验，不为形式新增测试。真实浏览器、服务或数据库验证仅在任务需要且具备条件时执行，遵守对应技能边界。
- 复用已通过且仍有效的结果；测试跳过、缺少环境、执行失败分别报告，不能算通过。

## 审查完整任务差异

开发结果交付前核对已确认范围和关键验收点，检查需求涉及的已有提交、暂存、未暂存及相关未跟踪文件。不能只审最后一次修改，也不能把其他人的无关改动当成本次成果。

按实际基线、任务提交及工作区变化确认范围；基线或任务归属不明确时说明缺口，不能声称完整审查通过。对照影响分析中的实际入口与相关分支，检查实现和验证是否漏掉同步方向、另一数据源或调用方；不能只检查已经修改的文件。重点检查需求遗漏、外部契约、兼容性、租户隔离，以及 SQL、配置和跨仓联动是否齐全。

首次合入 test 前，按拟合入版本完成上述审查；实现或范围变化后补审受影响部分。涉及业务配置时，追到实际读取、注入和刷新链路，核对未配置、空值及更新后的语义，不能只凭 setter 或 mock 测试认定配置生效。涉及前后端或多服务时，按同一操作场景核对各实际入口的结果，并标明尚未执行的环境验证。

小改动直接报告结论；复杂需求在计划中留简短审查记录。默认由当前 Agent 完成，不强制独立 Agent、独立报告或机器门禁；用户明确要求正式报告时再按要求扩展。

## 核对需求记录

已建档的任务在开发交付和提测前，按知识库规则核对处理方案正文、核心图（如有）、实际实现和测试预期是否一致。重点核对关键分支、优先级、兼容行为、配置生效和异常结果；方案变化时同步修正文、图和用例。拟采用方案与未核实行为必须明确标注，不能以设计图证明已经实现或验收通过。结果记入原主记录，不另建检查报告，不为本项检查强制给小任务建档。

对照最终任务 diff 和真实调用方，反查“影响范围与验收入口”是否覆盖全部受影响的菜单/功能及操作，尤其同页不同接口、历史数据源、下载/导出和共享组件旧入口。新增或缩小的影响同步更新；按场景关联验证版本与结果，未执行/未定位项不得记通过。非页面任务使用接口、定时任务或回调等实际入口。

## 证据对应版本

- 记录验证和审查针对的提交；有未提交改动时注明范围。测试读取整个工作区，不能把包含未提交依赖的结果宣称为某个 commit 单独通过。
- 跨会话恢复且 SHA 与范围不足以辨识未提交内容时，才记录差异指纹。指纹必须涵盖影响结果的暂存、未暂存和相关未跟踪文件，不能仅对 `git diff` 计算后声称覆盖全部内容。无法可靠比对就重新检查受影响部分。
- 提交、变更范围、配置、依赖或相关环境变化后，判断原证据哪些仍有效。相关变化需要补验和补审；无关文档变化不使所有测试失效。仅提交对象变化、实际内容未变时可复用已核实的结果。
- 例：A 版本测试通过后修改了相关实现，应报告“A 已验证，新增修改待验证”；待受影响检查完成再更新当前结论。
- 合入 test 后按 workflow 在合入结果上补核心验证；不把功能分支测试直接当作合入版本已通过。

## 完成与阻塞

实现完成、本地验证、测试环境验证、部署、运行态验收分别描述，并给出实际覆盖范围。相关路径尚未查清或未验证时保留该边界，不能因局部测试通过就宣称整个需求已完成。mock 测试不能证明真实接口有效，Pipeline 成功不能证明业务路径通过。

必要验证失败时先修复；无法继续则报告失败项和影响，不能提交失败状态或自动放行后续动作。只有用户明确接受限制且符合适用规则时才继续相关步骤，并在交付记录和最终汇报中保留限制。多个仓库或阶段部分完成时，逐项列明已完成、阻塞和未执行。
