# 功能 / Fix 交付流程

本文是 `work-feature-delivery` 的交付规则权威源，只在技能仓库维护。执行入口见 [SKILL.md](../SKILL.md)，按阶段读取所需章节。

## 适用范围

本文档用于记录 work 日常功能需求和 bug fix 的交付流程，覆盖从影响分析、拉分支、编码、提交、合并 `test`、生成测试清单、生成上线清单，到真实上线前合入上线分支的完整步骤。

本流程的 release / 个人功能分支规则适用于 work 业务仓库，不自动套用于 `.agent-toolkit`、个人项目或其他工具仓库；这些仓库遵守自身约定。

本流程适用于多个仓库同时改动的需求。每个仓库独立判断、独立建分支、独立提交、独立合并 `test`。

## 总体原则

- 先分析影响范围，再进入编码阶段；用户只是在问方案、判断、讨论时，不直接改代码。
- 默认控制 diff 规模，只改本次需求真正需要的代码，不顺手重排、格式化或重构无关内容。
- 修问题优先修源头，不为了规避跨项目修改而在当前项目加补丁。
- 每个仓库的个人功能分支必须是本地分支，不默认关联远程 upstream。
- `test` 分支只作为测试环境验证载体，不能直接等同于生产上线依据。
- 开发分支基线与目标上线批次是两个独立决策；不得根据其中一个推断另一个。
- 测试清单按需求生成，上线清单按发布批次聚合。
- 需要人工执行的 DDL 和一次性数据修复 SQL，完整内容只写在实际发布批次的上线清单；程序化迁移和测试初始化 SQL 仍保留在代码仓库。
- 测试清单和上线清单必须短而可执行：测试同学打开提测清单、发布同学打开上线清单，都应在第一屏抓住重点；禁止把计划文档、实现细节和测试矩阵整段搬进交付清单。

## 1. 影响分析

拿到新需求或 bug fix 后，先确认以下内容：

- 涉及哪些仓库。
- 涉及哪些模块。
- 涉及哪些可发布服务。
- 是否影响公共库、公共脚本、定时任务、批处理任务或跨服务调用链。
- 是否存在明确不处理的服务或模块。
- 是否需要数据库 SQL、配置变更、脚本变更或数据修复。

输出影响分析时，至少说明：

- 需要修改的仓库和模块。
- 预计需要发布的服务。
- 不需要发布的服务。
- 主要验证点。
- 当前判断依据来自代码、配置、调用链还是用户明确说明。

## 2. 拉分支规则

进入编码阶段前，先确认个人功能分支的 release 基线。非上线日、用户未指定且不存在发布窗口歧义时，默认从最新已确认可作为开发基线的 release 分支拉取；日期最新的 release 不等于当然可用的开发基线。

### 2.1 上线日基线确认

当天是常规上线日、存在与当天同日期的 release 分支，或当前 release 已进入冻结 / 发布窗口时，按以下规则处理：

- 用户已经明确指定基线分支时，直接按用户口径执行，不重复询问。
- 用户未指定时，先 `git fetch origin` 并核对当前、上一个 release 的真实远端引用，再询问本需求应基于哪个 release；获得明确答复前不得创建功能分支或开始编码。
- 询问应给出真实候选分支，例如：`今天是 release_20260827 上线日，本需求从 release_20260824 还是 release_20260827 拉分支？`
- 不得机械选择日期最新的 release，也不得机械回退到上一个 release。
- 多仓库需求逐仓库确认；只有各仓库基线一致且用户口径明确时，才可以合并为一次确认。
- 分支基线与上线清单批次分别确认。允许功能分支基于上一个 release，但需求仍进入当天上线清单；也允许功能分支基于当前 release，但需求安排到后续批次。

标准步骤：

```bash
git fetch origin
git switch release_YYYYMMDD
git pull --ff-only origin release_YYYYMMDD
git switch -c khh/fix-example
```

如果本地没有对应 release 分支，可以先从远程创建本地 release 分支，再创建个人分支：

```bash
git fetch origin
git switch -c release_YYYYMMDD origin/release_YYYYMMDD
git pull --ff-only origin release_YYYYMMDD
git switch -c khh/fix-example
```

关键规则：

- 个人功能分支用 `git switch -c <分支名>` 创建。
- 新建个人功能分支不得设置 upstream。
- 新建个人功能分支不得跟踪 release 分支。
- 分支名使用连字符，不使用下划线，例如 `khh/fix-xxl-job-timezone`。
- 只有明确需要推送个人功能分支时，才使用 `git push -u origin <个人分支名>` 建立远程同名分支跟踪关系。
- 默认在当前项目目录创建个人功能分支并开发；只有用户明确要求时才创建 worktree。
- 当前项目存在未提交修改、无法安全切换分支时，先汇报现状和影响，不迁移已有修改，也不自行改用 worktree。
- `customer-service-knowledge-base` 默认直接在 `main` 修改，不执行上述 release / 个人分支流程；提交和推送仍分别获得明确授权。

创建分支后记录基线：

```bash
git log -1 --oneline
git rev-parse HEAD
```

后续输出结果时必须说明个人分支来自哪个 release 分支，以及基线 commit 是什么。

## 3. 编码规则

编码阶段遵循当前仓库规则和全局工程约束。

重点要求：

- 不混入无关改动。
- 不删除原有注释，除非注释明显错误、过期或严重误导；确需调整时先说明原因。
- 关键路径、兼容逻辑、边界转换、非显而易见的业务规则必须补必要注释。
- 新增注释统一使用中文。
- 涉及状态、类型、来源、开关、业务编码时，先查是否已有枚举或常量；有统一定义必须复用。
- 处理 PII 数据必须脱敏。
- 多租户场景必须考虑企业隔离。

## 4. 本地验证

本地验证要跟本次改动范围匹配。

推荐顺序：

```bash
git status --short --branch
git diff
```

然后执行目标测试、编译或 lint。测试命令优先从项目文档、现有 CI、pom、脚本或已有测试习惯中确认，不猜不存在的命令。

如果单模块测试会解析到远端旧依赖，可以使用 Maven reactor 带上依赖模块，例如：

```bash
mvn -pl scheduler -am -Dtest=CleanCacheScheduledTest -DfailIfNoTests=false test
```

验证失败时默认停止，不提交失败状态。只有用户明确接受风险时，才可以继续后续步骤，并且必须在输出中说明未通过项和风险。

## 5. 本地提交

提交前先检查状态、暂存范围和身份。

推荐检查：

```bash
git status --short --branch
git config --show-origin --get user.name
git config --show-origin --get user.email
git config --show-origin --get commit.gpgsign
git config --show-origin --get user.signingkey
git var GIT_AUTHOR_IDENT
git var GIT_COMMITTER_IDENT
git remote -v
```

暂存文件必须显式列出，避免使用 `git add .` 带入无关内容。

暂存后检查：

```bash
git diff --cached --name-status
git diff --cached --check
git diff --cached --stat
```

必要时查看完整 staged diff，确认没有误提交：

```bash
git diff --cached
```

提交信息默认使用中文。一个仓库一个原子提交，不同仓库分别提交。

提交后检查：

```bash
git status --short --branch
git log -1 --oneline
git show -s --format='%h %an <%ae> | %cn <%ce> | %s' HEAD
```

提交完成后的输出必须包含：

- 仓库名。
- 当前个人功能分支。
- 来源 release 分支。
- 来源基线 commit。
- 当前本地 commit。
- 已执行的验证命令和结果。
- 是否 push。
- 是否仍有未提交或未跟踪文件。

## 6. 合并 test 与提测

合并 `test` 前必须先拉取远端 `test`，不能直接在过期的本地 `test` 上合并。

每个仓库标准步骤：

```bash
git status --short --branch
git switch test
git fetch origin test
git pull --ff-only origin test
git status --short --branch
git merge <个人功能分支>
```

如果本地 `test` 存在以下情况，必须停止并说明，不要硬合并：

- 工作区有未提交改动，且会影响切分支、pull 或 merge。
- `git pull --ff-only` 失败。
- 本地 `test` 与远端 `origin/test` 已分叉。
- merge 出现冲突。
- merge 前发现功能分支提交不是预期提交。

合并成功后检查：

```bash
git status --short --branch
git log origin/test..HEAD --oneline
```

合并后要在 `test` 分支上重新跑本次核心验证命令。验证通过后，才能推送 `test`。

推送前检查：

```bash
git fetch origin test
git rev-list --left-right --count origin/test...HEAD
git log origin/test..HEAD --format='%h %an <%ae> | %cn <%ce> | %s'
```

`git rev-list` 结果必须是 `0 N`，表示本地不落后，只领先远端。不是 `0 N` 时，不要 push，先说明分支状态。

确认无问题后推送：

```bash
git push origin test
```

推送后检查：

```bash
git status --short --branch
git rev-list --left-right --count origin/test...HEAD
```

推送完成后的输出必须包含：

- 每个仓库的 `test` merge commit。
- 每个仓库推送前的领先 / 落后检查结果。
- push 结果。
- push 后本地与远端是否同步。
- 仍存在但未参与提交的未跟踪文件。

## 7. 测试清单

测试清单按需求或 fix 生成，一次需求一份。

只有需要明确交付测试同学验证的业务需求或 Fix，才默认生成测试清单。个人项目、Skill、脚本、CI、文档、内部基础设施、纯配置和本地工具调整默认不生成，除非用户明确要求。

### 7.1 读者与目标

- 主读者是测试同学，不是开发自己的实现笔记。
- 目标：打开文档后 30 秒内能回答「测什么、从哪进、测前做什么、P0 验什么」。
- 测试清单不承担整批上线编排；发布服务汇总、发布顺序、回滚写在上线清单。
- 短模板见 `~/data/work/docs/templates/requirement.md`。生成时按模板裁剪，不要为了“章节齐全”而灌水。

### 7.2 目录与命名

测试计划、用例和结果维护在需求唯一主记录：

```text
~/data/work/docs/delivery/requirements/<需求或 Fix ID>/index.md
```

编号与主记录字段遵循知识库 `AGENTS.md` 和 `templates/requirement.md`。复用已有记录，不再按测试日期创建独立提测文件；内容确需拆分时，在同一需求目录使用 `testing.md` 并由主记录链接，总进度只在主记录维护。

### 7.3 复杂度分级

生成前先定级别，再决定厚度：

| 级别 | 典型场景 | 正文目标 | 核心验证 |
| --- | --- | --- | --- |
| S | 单接口、单字段、小 Fix | 25～40 行 | 3～5 条 |
| M | 前后端联调、导入导出、常规需求 | 40～80 行 | 5～8 条 |
| L | 多服务重构、客户定制、含 SQL/配置 | 60～100 行，硬上限 120 行 | 5～8 条 P0；确有需要时另加附录，且标注非阻塞 |

默认按 M 级写。只有影响验收的真实复杂度才升到 L，禁止把 S/M 需求写成 L。

### 7.4 推荐结构（固定顺序）

```markdown
# <一句话需求名> 提测清单

- TAPD / 关联计划：（链接即可，不复述正文）
- 发布服务：...
- 不发布：（仅当容易误发时写）

## 测试入口
## 测前准备
## 核心验证
## 回归边界
## 不在本轮范围          ← 有才写
## 风险卡点              ← 有才写，0～3 条
```

| 章节 | 必写 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| 标题元信息 | 是 | TAPD/计划链接、发布服务；易误发时补「不发布」 | 功能分支、基线 commit、merge SHA、模块类清单 |
| 测试入口 | 是 | 页面路径，或无 UI 时的 1 个主接口 | 全量 URI、内部方法名 |
| 测前准备 | 是 | 企业/数据样例；人工 SQL 所在上线清单与执行时机；程序化迁移路径；配置 key 与动作（追加/删除/不要配） | 可执行 SQL 正文、整段 Nacos JSON、Schema 全文、代码推导过程 |
| 核心验证 | 是 | 用户可见结果、回调结果、开关差异；默认 5～8 条 | 实现说明、状态机全分支、JUnit/lint/构建 |
| 回归边界 | 是 | 最易误伤的 3～5 条 | 「所有旧行为不变」空话 |
| 不在本轮范围 | 否 | 明确不测的历史数据、重构、协议扩展 | 与回归重复的内容 |
| 风险卡点 | 否 | 会改变测法或上线顺序的卡点，最多 3 条 | 性能品味讨论、与核心验证重复的内容 |

### 7.5 生成规则

1. 先从需求/计划抽出不超过 5 条用户可见变化，每条对应 1 个 P0 验证点。
2. 每个发布服务至少 1 条可观察验证；禁止按「服务 × 场景」做笛卡尔积展开。
3. 验证点写可观察结果，不写实现路径。正确示例：「第一次回调 `intentTag` 为原始意向」。错误示例：「`CallbackChainHandler.shouldSkipCallback` 因…」。
4. 计划中的业务口径、状态机、字段表、长配置样例：只给链接和必做动作，不抄正文。
5. 人工 DDL / 一次性数据修复 SQL 只保留：上线清单链接、执行时机、漏执行现象（一句），不复制 SQL 正文；程序化迁移只写仓库路径。配置只保留 dataId、操作类型和漏配现象。
6. 多语言全量抽查、性能 EXPLAIN、审批全状态矩阵：默认不进正文。用户明确要求，或 L 级且影响验收时，可放「附录：扩展用例」并标注非阻塞。
7. 分支名、commit、merge SHA：不进提测清单；需要时写在上线清单合入摘要或开发汇报中。
8. 生成后自检：是否复述了计划？是否超过级别行数上限？是否出现 SHA/类名/整段 JSON？命中则删除或改为外链。

### 7.6 内容归属

| 内容 | 放哪里 |
| --- | --- |
| 业务口径、状态机、字段设计 | 计划文档或项目 `docs/` |
| 怎么测、P0 验收 | 提测清单 |
| 发什么、顺序、人工 SQL 完整内容、配置动作、回滚 | 上线清单 |
| 分支 / commit 交付记录 | 上线清单合入摘要或对话汇报 |

## 8. 上线清单

上线清单按发布批次聚合，不按单个需求拆分。

work 常规上线日为每周四。上线清单文件名使用本批周四上线日期。

### 8.1 读者与目标

- 主读者是发布 / 值班同学，不是第二份测试说明书。
- 目标：一眼看到本批发什么、有无 SQL/配置、顺序、卡点、冒烟和回滚。
- 短模板见 `~/data/work/docs/templates/release.md`。追加需求时只增量更新，不把提测全文粘贴进来。

### 8.2 目标批次确认、目录与命名

上线清单的目标批次必须独立确认，不能从开发分支基线或代码交付状态推断：

- 用户已明确指定上线日期或“本周 / 下周 / 当前批次”时，按用户口径更新对应清单。
- 当前日期已晚于最近一次常规上线日，且用户未明确要求补丁、追补或补记历史批次时，默认进入下一次常规周四上线清单，无需询问。
- 只有处于上线日或发布窗口内，或者用户明确提到补丁、追补、历史批次但目标日期不明确时，才确认写入当前批次还是下一批。
- 不得根据功能分支来自上一个 release，就默认需求属于下一批；不得根据代码已合入 `test`、开发发生在上线日或当前 release 已冻结，就自动选择当前批次或下一批。
- 分支基线、`test` 状态、上线清单批次、上线分支合入和生产发布是五个独立状态，清单中按真实状态分别记录。
- 同一发布批次已有清单时，只增量更新现有文件，不为单个需求创建重复清单。

上线日需要同时确认分支基线和清单批次时，可以一次询问两个独立问题，例如：`功能分支从哪个 release 拉？上线清单记入 20260827 还是下一批？`

目录：

```text
~/data/work/docs/delivery/releases/
```

命名规则：

```text
yyyyMMdd.md
```

示例：

```text
20260716.md
```

发布批次文件按实际批次日期命名；需求记录引用批次，不与需求目录编号混用。

同一周多个需求都追加到同一份上线清单。临时补丁不走周四常规上线时，按实际补丁上线日期单独生成一份上线清单。

### 8.3 厚度与聚合

- 整批目标：约 80～120 行；多需求批次可到 150 行，但发布后验证仍保持冒烟级。
- 每个需求在批次中的增量：优先控制在约 15 行内（需求表一行 + 物料/顺序/冒烟/回滚要点）。
- S 级 Fix：需求表一行带过，不为它单独开大段「上线前检查」。
- 同一服务被多个需求命中：发布服务表合并为一行，备注写清需求编号。

### 8.4 推荐结构（固定顺序）

```markdown
# yyyyMMdd 上线清单

## 一页摘要
## 发布服务
## 变更物料
## 代码合入摘要            ← 短表即可
## 发布顺序
## 上线卡点
## 发布后冒烟
## 回滚
```

| 章节 | 必写 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| 一页摘要 | 是 | 日期、状态；需求表（名称 / 仓库 / test 状态 / 有无 SQL·配置 / 提测链接） | 长备注复述方案 |
| 发布服务 | 是 | 本批实际要发布的服务、仓库、一句发布原因 | 「不发布服务」清单；逐文件改动说明 |
| 变更物料 | 是 | 人工 SQL 写完整可执行内容；程序化迁移写仓库路径；配置 / 脚本 / 翻译写类型、需求、动作和权威来源；无则写「无」 | 翻译 key 超长列表（>5 时改链提测或计划） |
| 代码合入摘要 | 是 | 仓库、功能分支、是否已合入并推送 `test`；可选 1 个关键 commit | 类名、文件列表、本地验证流水账 |
| 发布顺序 | 是 | 有依赖写编号；无依赖写「可并行」 | 无信息的重复列表 |
| 上线卡点 | 是 | 整批通用 3～5 条；仅高风险需求各加 1～3 条 | 复制提测全部 checkbox |
| 发布后冒烟 | 是 | 整批 3～6 条；每需求 1～2 条；详情链提测 | 复刻提测核心验证全文 |
| 回滚 | 是 | 按服务或批次；共用 server 时注明 commit 级回退注意 | 与风险节重复的长文 |

默认**不要**写「不发布服务」章节。发布范围以「发布服务」表为准；依赖未改、脚本只录入不发版等，需要时在变更物料或卡点用一句话带过即可。

### 8.5 生成与追加规则

1. 新需求进入本批时：更新需求表、发布服务、变更物料；按需补顺序、卡点、冒烟、回滚。
2. 人工 DDL 和一次性数据修复 SQL 必须在实际发布批次中写出完整可执行内容、执行环境和执行时机，不在代码仓库另建 SQL 文档；程序化迁移只写仓库路径。
3. 发布后验证只写冒烟，详细用例一律链关联提测清单。
4. 禁止把提测「核心验证」「回归边界」「风险」整节复制进上线清单。
5. 风险只保留影响发布顺序、配置前置或回滚策略的条目。
6. 负责人与确认状态：需要时在需求表加一列即可，不单独展开长节。
7. 生成后自检：是否出现第二份测试矩阵？是否多余写了「不发布服务」清单？合入信息是否超过「分支 + test 状态」？人工 SQL 是否完整可执行、程序化迁移是否有路径？

### 8.6 上线 SQL 输出规则

- 上线清单中的 SQL 代码块只列本批实际需要执行的变更语句；执行库和时机用一句正文说明。
- 不附带 `SELECT DATABASE()`、`SHOW COLUMNS`、`SHOW CREATE TABLE`、前后核查查询、可选历史清理或备用 SQL。只有用户明确要求这些内容时再提供；必要的只读核对在准备阶段完成，不混入执行清单。
- MySQL / InnoDB 表结构变更必须使用目标版本和操作支持的在线 DDL，通常显式指定 `ALGORITHM=INPLACE, LOCK=NONE`；不能把裸 `ALTER TABLE` 当作在线 DDL。
- 不支持上述在线方式时，不去掉算法或锁约束，不自动降级为 `COPY` 或阻塞写入的方式；先说明具体限制，再确定可用的在线变更方案。不得未经版本核实统一改成 `INSTANT`，也不得给非 MySQL 数据库套用这些语法。
- 保留“仅生成、尚未执行”的真实状态；生成上线 SQL 不代表获得数据库执行授权。

## 9. 真实上线前合入上线分支

真实上线时，不能直接把 `test` 分支当成生产依据。

上线前必须确认最新上线分支：

- 可能已经存在。
- 也可能需要从上一个 release 或当前生产基线重新创建。

合入上线分支时，使用已经在测试环境验证通过的个人功能分支或对应 commit，不盲目把 `test` 分支整体合入上线分支。

上线分支合入前必须检查：

- 上线分支基线是否正确。
- 是否混入 `test` 上其他未确认需求。
- 本次需求对应 commit 是否完整。
- 是否包含所有相关仓库。
- 是否需要同步 SQL、配置或脚本。
- 是否需要补充或更新本批上线清单。

## 10. 常见错误

以下行为默认禁止：

- 未做影响分析就直接编码。
- 用户只是在讨论方案时直接改代码。
- 从 release 分支创建个人分支时设置 upstream。
- 个人分支跟踪 release 分支。
- 上线日未确认开发基线，就机械使用当天 release 或上一个 release 创建功能分支。
- 用户未明确要求时自行创建 worktree。
- 当前工作区不适合切分支时擅自迁移已有修改。
- `git add .` 带入无关文件。
- 跳过本地验证直接提交。
- 本地 `test` 未先 pull 远端就 merge。
- `test` 已分叉或 `pull --ff-only` 失败时继续硬合。
- 把 `test` 分支直接当作生产上线分支。
- 根据功能分支基线、`test` 合入时间或开发日期推断上线清单批次，或默认上线日的新需求都属于下一批。
- 每个需求都生成一份最终上线清单，导致发布批次口径分散。
- 为人工执行的 DDL 或一次性数据修复 SQL 在代码仓库另建 SQL 文档，导致上线清单不能独立执行。
- 删除原有注释或新增英文注释。
- 把计划全文、实现类名、整段配置 JSON、分支 SHA 写进提测清单。
- 提测核心验证超过 12 条，或把状态机/单测矩阵当验收用例。
- 上线清单复制提测验证全文，或把上线文档写成第二份测试说明书。
