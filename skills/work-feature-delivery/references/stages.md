# 阶段衔接

阶段用于选择下一步，不是每次必须顺序执行的状态机。[交付规则](delivery-workflow.md)（下文 workflow）章节号仅供定位，以当前章节内容及目标仓库规则为准。

| 阶段 | 核心动作与复用能力 | 本阶段交付证据 |
|---|---|---|
| 需求与影响分析 | TAPD 来源用 `tapd-story`，其他来源直接读取；结合代码定位仓库、模块、发布服务、SQL/配置及验证点，参照 workflow §1 | 已确认行为、排除范围、代码依据、拟采用处理方案及必要待确认项 |
| 必要澄清 | 仅对影响结论的业务歧义使用 `grilling`；稳定术语和难逆决策按需交给 `domain-modeling` | 确认口径；只要求方案时在这里交付，不开始开发 |
| 基线与实现 | 按 workflow §2–3 核对发布窗口、基线和工作区，再创建分支、实施；已有功能分支先核对，不重复创建 | 每仓基线 ref/SHA、功能分支及实际实现范围；同步主记录中的实际处理方案与图文 |
| 验证与审查 | 按 §4 及 verification.md 验证本轮行为和完整任务差异；按需使用 `local-browser-verify`、`verify-test-db` 等 | 对应版本的检查结果、审查发现、未验证边界；方案图文、实现和验收预期一致 |
| 本地提交 | 明确授权后使用 `git-commit`，衔接 §5，复用仍有效的验证 | 每仓 commit、实际提交范围、剩余改动及签名情况 |
| 合并 test 与推送 | 按 §6 核对真实远端、预期功能提交和工作区；合入后补核心验证，推送按授权处理 | test 合入结果、合入后验证、推送状态，分别记录 |
| 提测及上线物料 | 按 §7–8 及现有模板维护短清单；新增受保护接口按需使用 `work-url-permission-sql` | 可供测试理解处理逻辑和执行验收的需求主记录、独立确定的发布批次及清单、物料状态 |
| release 合入、构建与验收 | 按 §9 确认上线基线和已验证功能提交，依授权合入；构建用 `gitlab-run-pipeline`，运行态按需使用浏览器、日志、监控能力 | 实际合入与推送结果、Pipeline ID/实际 SHA、运行态验收证据 |

## 授权与恢复

- “开发/修复”默认包含实现、本地验证、审查及结果汇报，不自动包含提交、推送、合并、部署或数据库写入。
- “继续提测”等表达先结合会话中的既有授权判断；仅对尚未明确且实际需要的外部动作确认，不要求用户重新授权整个流程。
- 清单可在相应代码操作前准备，但必须标明尚未提交、未合入、未推送等真实状态，文档生成不代表环境已更新。
- 恢复时核对与下一步相关的 Git 状态、计划范围和证据版本。远端 freshness、合入及推送前检查沿用 workflow 和对应技能。
- 代码有变化先按影响补验；基线或分支不符、存在冲突、关键证据缺失时说明具体阻塞。能独立完成的分析、材料准备或其他仓库工作可继续，不擅自覆盖现场。
- 多仓分别报告成功、失败和未执行项，不因一个仓库成功就宣布整个需求交付完成。

## 材料归属

需求主记录统一维护范围、处理方案、测试验收和实施证据；详细设计或测试矩阵确需拆分时放在同一需求目录并链接，主记录保留可独立理解的方案摘要和唯一总进度。内容规范以知识库规则及模板为准。上线清单描述批次服务、物料、顺序和异常处理。人工 SQL 的完整内容只保留在实际批次上线清单，程序化迁移保留代码路径，不复制维护多份正文。
