# 阶段衔接

本文在 [通用阶段](../../feature-delivery/SKILL.md) 上补充工作环境动作和证据，只执行当前任务适用阶段。[交付规则](delivery-workflow.md)（下文 workflow）章节号仅供定位，以当前章节内容及目标仓库规则为准。

## 按当前材料选择入口

先判断本轮目标、已有材料与授权，再选择入口。入口不等于交付类型；独立功能、性能优化、重构等业务代码交付的 TAPD / 主记录要求，以及 Bug Fix 的编号例外，统一见 [workflow §1.3](delivery-workflow.md#13-入口收敛与正式建需)。

| 当前材料 | 先做什么 | 转入哪里 |
|---|---|---|
| 给需求 ID | 按 §1.1 恢复本地主记录、核对真实实现与验证，再按需补 TAPD；复用已确认口径 | 完成必要探索与澄清后进入当前授权阶段，不将每次给 ID 都当作新任务 |
| 无 ID 讨论想法 | 明确目标，交替探索与 `grilling`，收敛成范围、排除项和验收草稿；默认先留在对话 | 按 §1.3 判断交付类型；需新增 TAPD 时，有明确创建授权才通过 `tapd-story` 建需拿真实 ID，再建本地主记录；有实施授权及前置条件才开发，认可方案不新增这些授权 |
| 故障现象 | 先排查或复现，区分已确认缺陷、配置问题与预期差异，再澄清真正影响修复或验收的口径 | 可得出无需改代码的结论；确需修复时复用原 ID，仅已确认无 TAPD 的 Bug Fix 可按既有规则使用稳定 `fix-` 编号，再依授权修复和验证 |
| 继续任务或测试反馈 | 恢复原主记录、代码状态与验证版本，对照本轮反馈，只补新增或冲突口径 | 继续原需求的开发、验证或收尾；仅新增独立范围时按 §1.3 单独建需 |
| 已有方案或代码 | 核对实际成果、适用范围、版本及证据，识别已完成与剩余工作 | 按本轮目标直接进入实施、审查、验证或收尾，不重写已完成代码或重问已确认口径；有代码无记录不等于从未开发，恢复时不编造历史 |

纯问答、只读排查、纯专项审查或提交，以及工具箱和本地工具维护，继续按适用范围轻量处理，不强制补 TAPD 或重走开发。发现代码问题也不自动取得修改授权；若后续进入业务代码实施，再检查该阶段前置条件。

## 当前阶段的动作与证据

| 阶段 | 核心动作与复用能力 | 本阶段交付证据 |
|---|---|---|
| 需求与影响分析 | 先按 ID 恢复本地主记录与实现状态，需补远端需求时用 `tapd-story`；定向检索相关知识，再定位仓库、加载规则并核对代码，方法见 workflow §1 | 已有或明确要求创建主记录时保存确认行为、菜单/功能级影响范围、代码依据、拟采用方案及未决项；纯问答或只读排查且无记录时留在对话 |
| 边界收敛与必要澄清 | 所有准备实施的新任务均按 workflow §1.3 显式检查边界；真实未决项交给 `grilling` 一次一问，需要证据时返回探索，无未决项时简短说明已确认；稳定术语和难逆决策按需交给 `domain-modeling` | 汇总范围、排除项、验收、待验证项与下一阶段；已有主记录及时更新关键回答。口径已定而未实现时记待开发，该状态不表示实施授权。涉及客户对接时，稳定流程与差异并入对应客户文档，建档遵循既有边界 |
| 基线与实现 | 获得实施授权后，先按 [实施前检查](delivery-record.md#实施前检查) 恢复并更新或建立最小主记录，再按 workflow §2–3 核对发布窗口、基线和工作区；首个业务代码修改或委派实现前必须完成，单仓小改不免建档；已有功能分支先核对，不重复创建 | 实际主记录路径、每仓基线 ref/SHA、功能分支及实际实现范围；同步实际处理方案与图文。客户对接实现完成后，对照最终代码核实客户文档的业务入口、时序图、特殊处理和参数示例 |
| 验证与审查 | 按 §4 及 verification.md 验证本轮行为和完整任务差异；按需使用 `local-browser-verify`、`verify-test-db` 等；开发结束或本轮收尾前完成 [记录与材料检查](delivery-record.md#更新时机)，不等待提测或合入 `test` | 对应版本的检查结果、审查发现、未验证边界；方案图文、实现和验收预期一致；实际主记录、批次清单双向链接，或已在主记录保存批次待定原因、物料和下一动作 |
| 本地提交 | 明确授权后使用 `git-commit`，衔接 §5，复用仍有效的验证 | 每仓 commit、实际提交范围、剩余改动及签名情况 |
| 合并 test 与推送 | 按 §6 核对真实远端、预期功能提交和工作区；合入后补核心验证，推送按授权处理 | test 合入结果、合入后验证、推送状态，分别记录 |
| 提测及上线物料 | 按 §7–8 核对并完善开发收尾时已检查的主记录和批次清单，不等到本阶段才补建；新增受保护接口按需使用 `work-url-permission-sql` | 可供测试理解处理逻辑和执行验收的需求主记录、独立确定的发布批次及清单、物料状态。客户对接首次提测或交接前，检查客户文档能否独立阅读和用于配置，过程证据与工具说明是否归位，未知状态是否准确 |
| release 合入、构建与验收 | 按 §9 确认上线基线和已验证功能提交，依授权合入；构建用 `gitlab-run-pipeline`，运行态按需使用浏览器、日志、监控能力 | 实际合入与推送结果、Pipeline ID/实际 SHA、运行态验收证据；涉及客户对接时，按实际证据更新客户文档适用状态和受影响的原章节 |

## 阶段完成与跳转

- 探索取得足以判断下一步的事实后，交给边界收敛检查；缺代码、配置或运行证据时继续定向探索，不把可查事实当成用户选择。
- 每个准备实施的新任务都显式核对范围、排除项、验收和真实未决项。需用户决定时一次只问一个问题；无未决项时说明已确认，不要求固定澄清轮数或再次认可方案。继续任务只检查本轮新增或冲突范围。
- 无 ID 讨论收敛后按 workflow §1.3 进入建需或停留在草稿；编号、主记录实际落盘、实施授权及 §2 基线等条件满足后，才进入业务代码修改或委派实现。已具备创建或实施授权时连续推进，不追加统一开工确认。
- 已有方案、代码或验证可复用时，直接进入本轮需要的阶段；开发结束或本轮收尾时仍完成适用记录与材料检查，专项只读或提交请求则在其授权终点交付。

## 授权与恢复

通用授权、恢复与阻塞处理按 [通用流程](../../feature-delivery/SKILL.md) 执行。工作环境恢复顺序按 workflow §1.1，远端核对、合入及推送前检查按对应团队阶段执行。清单可提前准备，必须标明尚未提交、未合入或未推送的真实状态；文档生成不代表环境已更新。

建档编号或写入受阻时先完成独立只读调查，不先改业务代码；批次未定只阻塞对应清单归档，不阻塞其他前置条件已满足的授权开发。结束时报告实际更新的主记录、批次清单路径或待定原因，不能因本轮只实现和本地验证而省略适用材料检查。

## 材料归属

需求主记录统一维护范围、处理方案、测试验收和实施证据；详细设计或测试矩阵确需拆分时放在同一需求目录并链接，主记录保留可独立理解的方案摘要和唯一总进度。内容规范以知识库规则及模板为准。上线清单描述批次服务、物料、顺序和异常处理。人工 SQL 的完整内容只保留在实际批次上线清单，程序化迁移保留代码路径，不复制维护多份正文。

客户文档阶段动作仅适用于涉及客户对接的任务；已有业务线优先更新原文档，后续需求重新执行受影响阶段的检查。结构、阶段完成标准和信息归属以知识库 `AGENTS.md` 的“客户对接文档规则 → 文档演进与阶段维护”及 `templates/integration.md` 为准，不在技能内维护第二份正文模板，不要求一般开发任务创建客户文档。
